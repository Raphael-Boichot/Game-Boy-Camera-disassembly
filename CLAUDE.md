## Gotchas learned
* BGB runs a demo (one joypad byte per frame; 250-frame boot hold, then free frames) and gives a screenshot and the state at the end; mode `$D5CE`, state `$D5CF`. BGB needs 3 more boot frames than the core.
  Message states advance by themselves: use long waits and no extra key. Two CPUs: use 2 workers (about 250 BGB runs in 4 minutes). The live camera view needs title A and two more A presses.
  BGB's sensor picture is fake (§18.9): it reproduces the code path, not pixel-dependent decisions.
* `-screenonexit` in BGB saves only the 160 x 144 LCD; to see the Super Game Boy border run BGB with `SystemMode=2` in a visible window under Xvfb (`tcrf_check/tools/bgb_sgb_capture.sh`).
* Long jobs in the background (`setsid nohup`); a foreground tool call over 120 s is killed. Never `pkill -f` a pattern that appears in your own command line (use the `[x]` trick or kill by PID).
* Linked BGB runs (printer helper, `-connect`) stalled at the handshake with `-hf` in the sandbox: set `BGB_HF=-headless` (`bgb_run.py` reads it). `PRN_ERR=CMD:N:HEX` makes the helper answer a chosen status byte (§16.16).
* mgbdis must be master after the v3.0 tag (commit 95d951a): v3.0 ignores the `.data` row width and `.padding`, and the round trip still passes while `sym_fix.py` rewrites almost no table (the checker's `sym_fix stats` line fails). The checker expects `/home/claude/tc/mgbdis` and `/home/claude/tc/rgbds`.
* Other BGB and core pitfalls (VRAM writes in PPU mode 3, hex logs, WAV offset, forcing, two-pass snapshots): `HOWTO_NEW_ROM.md` §6 and §7.
* **BGB, used efficiently (it is the judge: ask it, do not argue from the core or from reading alone).**
  * *One run answers a whole list.* `tcrf_check/tools/bgb_wp_probe.py CORPUS ENTRY WATCHPOINTS OUTPREFIX` replays a corpus entry with BGB **logging watchpoints** (`-wp`, comma separated, `ADDR[-ADDR]/VALUE/FLAGS/MESSAGE`, flags from `drwxj`, banked ROM addresses as `BB:AAAA`; `D5F0-D5F2//rw/CUR` for WRAM, `07:4C8D//x/ENTRY` for an execution). BGB writes the message to `debugmsg.txt` at every hit and keeps running, so the count per message proves or refutes a read, a write or an execution.
    Always add a CONTROL watchpoint on a byte the replay certainly touches: then 0 means "not accessed", not "watchpoint broken". A new command line gets one short test run before a batch.
  * *Put the context in the message.* BGB expands expressions between `%`: `%pc%` (the address of the accessing instruction: BGB stops before it runs), `%rombank%`, `%a%`, `%(d5ce)%` / `%(d5cf)%` (mode / state), `%(d5f2)%` (the byte itself: the value read, or the value BEFORE a write; the value written by `ld [nn],a` is `%a%`). A log line is then (access, site, screen, value) and the count of equal lines is a table: no second run is needed to learn in which screen a site fires. `tcrf_check/tools/wram_probe.py` and `wram_probe_report.py` do this for the weakly tagged RAM names (README §2.13).
  * *Batch it.* One command line took 120 watchpoints with messages of about 60 characters; use chunks above that. Replay the cheapest organic corpus entry of each mode / state signature instead of long random runs. Two workers, each with its own copy of the BGB folder (`BGB_DIR`; the ini and `debugmsg.txt` are per folder), started with `setsid nohup`, polled with short calls, with a partial result written after every replay.
  * *Frame by frame.* A short run (demo of a few hundred frames) costs 1-2 s in BGB, a run with a 650-frame prefix several seconds: 300 runs, one per game frame, take 5-10 minutes on two workers. The picture (`-screenonexit`) is the frame displayed at the end of the demo and the state can be a fraction of a frame ahead of it (a copy in progress): trust the picture for what is on screen. Sample every 2-4 frames when 1-frame resolution is not the question (`tcrf_check/tools/menu_screen_gif.py capture`, a demo ending n frames after a key press: `[('A',4,300),('Select',min(n,4),max(n-4,0))]`).
  * *Classify every hit, drop none.* Cold boot (`Mem_Zero`) writes every WRAM byte once: that is the baseline, not a use. A hit that the access table does not list is a pointer-based access (its routine holds the `P` row) or a new finding; a static site that never fires in the replays is "not reached here", not "dead".
  * *Two-player, printer and menu-only screens need a driver, not a corpus entry.* `tcrf_check/tools/wram_probe_scen.py` runs the same watchpoints through the linked exchange (`bgb_link_wp.py`, two BGB processes; `WPS_SENDER` gives the sender its own list), the printer runs (`bgb_print_run.py`, `bgb_print_wild.py`, `bgb_dj_print.py`, `PRN_ERR=` injects a status) and the Run! races (`bgb_run_race.py`); every other BGB script takes the list from the environment variable `BGB_WP` (`bgb_run.py`). A corpus root named `_zero` / `_ff` is a pseudo-save of 128 KB of `$00` / `$FF`: BGB has no such file, so it must exist in `saves_pseudo/` or the replay ends on the boot menu. A long corpus path recorded in the core can end on another screen in BGB (timing): the hits are still valid because each one carries its own mode, but check the `end` line before reading a verdict from it.
  * The end state (`-stateonexit`: WRAM, VRAM, OAM, registers; `bgb_run.read_state`), the picture (`-screenonexit`) and a breakpoint (`-br`) cover the rest; a free-running counter or a value known only inside a frame needs a watchpoint message, not a state dump.
* **TCRF pictures can be 2x enlargements:** reduce them before matching (`tcrf_check/tools/tcrf_exact_match.py`), allow palette folds and tile flips, and remember that ROM tile sheets are 16 tiles wide with rows 0x100 bytes apart.
  A 1-tile or 2-tile exact match is weak: check the display evidence. When the aligned matcher finds nothing, the picture is not necessarily a whole tile: a glyph can sit anywhere inside a blank tile
  (`dj_marker_tile.py`) or straddle two stacked tiles, which then shows as one tile at an odd offset (`run_star_pair.py` searches 8 x 16 blocks, the OBJ 8 x 16 mode; the star's single-tile "candidate" `1B:618A` was this). Count only the hits on a 16-byte boundary as tiles.
* A load site `ld hl,TABLE; add hl,bc; ld a,[hl+]` before a banked copy is a local pointer table, not a far pointer; and a 3-byte record table is a far-pointer table only if its reader hands the three bytes to a banked copy (the podium records `09:65CA` / `09:65FB` are `{x; y; entry}`, not `{lo,hi,bank}`). The auto labeller turns any executed 16-bit immediate equal to a ROM address into a label
  (`ld bc,$xxxx` before an OAM meta-sprite call is a position): read the code before trusting a label that cuts a table.
* **A `?`, `_Aux` or `_Unref` label (or any "by eye" note) is a hypothesis: re-derive it before trusting it.** Exact tile match of every tile over the whole ROM and the other ROM, a loader scan (immediates with the bank, pointer tables,
  `assets/copy_sites_jp.csv`), then the display tracker (it is value-matched: check that the tiles have no duplicate elsewhere). Three of the eight `?` labels changed this way (`0C:6AB0` "kana strips" was 336 B of `$00` and 3 tiles).
* **Maps:** 18 rows of 32 bytes (0x240 B; 20 visible columns, 12 hidden), in chains 0x240 apart (`25:73A0 / 75E0 / 7820 / 7A60`, `26:6C00 / 6E40 / 7080 / 72C0`); the bank-27 album maps are 22-row copies that overlap on purpose. Check a start against the
  neighbours and the hidden columns, and type the rows `data,32,Map` (`data,16,Gfx` is for tile sets). In `sym_types_jp.csv` the rows are applied in order and the LAST row wins. A seam search with a shuffled-neighbour control is evidence only for whole maps
  and lower halves (an upper half does not recover true blocks).
* **Keep `26:7080` in mind for other ROMs** (owner's request 2026-10-19): that map (README §16.25.2) has no tile set, loader or look-alike in the two Pocket Camera ROMs. When a ROM of another build or title shows a full-screen map of the same fingerprint (576 B, `$A5` hidden columns, ~245 ids numbered by first use in a descending raster, strip + 16-column picture + two small blocks), run `tcrf_check/tools/map_pattern_match2.py` and then `tile_seam_offsets.py` as `HOWTO_NEW_ROM.md` Stage C item 6 says: a hit gives the missing tile set.
* **A label that carries an address carries its own** (`Gfx_BB_AAAA_Consumer`); a piece of a parent asset is `_Part<addr>` (own address) or `_Cont`. Exceptions live in the checker's `ODD_MAP_ROWS` / `GFX_ON_MAP` lists, with the reason.
* **Generated files with hand-kept parts or frozen inputs:** `display_report.py` overwrites the hand tail of `really_unused.md` (restore it from git after every run); `open_assets.csv` is a frozen candidate list that `display_report.py` reads, so it is not
  regenerated from the current doubts list (the README says so). Regenerating the layout / reachability pictures needs `--rom`.
* Do not recompute what the README already states; check the section list at the top, §12 (open items) and §16.10 first.
