## 17. Printing in BGB (printer helper), the print features, and the BGB coverage re-trace

Evidence tags as before: **C** = reproduced in BGB (or code-traced and reproduced in my core), **I** = inferred, **?** = not established. Everything in 17.1-17.6 was produced with BGB 1.5.x under Wine, headless, with the **Game Boy Printer helper** of 17.1 attached through BGB's link; the printed pages are the helper's output (`tcrf_check/assets/bgb_printer/`).

### 17.1 A printer for BGB: `tools/bgb_printer.py` (C)

BGB has no printer that can be switched on from the command line; the printer is a **link partner**: BGB is started with `-connect 127.0.0.1:PORT` and a program on that port speaks the BGB link protocol (TCP, 8-byte packets `b1 b2 b3 b4 i1` with `i1` little-endian: 1 version, 101 joypad, 104 sync1 = master byte, 105 sync2 = slave reply, 106 sync3 = timestamp sync, 108 status, 109 want-disconnect). `bgb_printer.py` is such a partner (library class `PrinterServer`, TCP, one thread) plus the usual printer state machine (magic `88 33`, command, compression flag, 16-bit length, data, 16-bit checksum, replies `81` and status). What the helper has to do to keep BGB running (found by **sniffing a BGB-to-BGB link**: `tools/bgb_link_sniff.py` is a TCP relay between a listening and a connecting BGB that logs every packet): answer BGB's version packet with *status 4* (support reconnect), the undocumented **packet 158** (`i1` = 19060) and *status 5* (running); answer every sync1 with a sync2 (`b3 = $80`) carrying the printer reply; **echo every sync3** (BGB sends one every 2048 cycles, so about 2,000 per emulated second, and waits for the echo). A linked BGB runs at about 50-60 frames per second; the same lineage without the helper takes a few seconds (C, wall-clock).

Reply model: copied from the **real printer traces** supplied with the project (Arduino captures of the Camera printing, `Game_Boy_Camera*.txt`): INIT → `00`; first DATA `00`, DATA after DATA `08`; INQUIRY `00` (clears the flag); **PRINT → `08`**; then INQUIRY `06` while "printing", `04` twice, then `00`. The helper answers 20 busy polls instead of the real printer's ≈140 (`PRN_POLLS`). Two lessons (C): a PRINT reply of `06` made the Camera send PRINT again and again (completion routine `00:196F`, §2 `$DC3B`; seen in my core and in BGB), the real `08` does not; and a **killed run leaves X servers and BGB processes behind that make the next linked run stall right after the handshake** (only version + one status packet ever arrive): kill them (`pkill -x Xvfb`, then the `bgb.exe` Wine processes) before starting again. (In the session of §16.16 the stall also came from the BGB option `-hf`: a linked run with `-hf` stalled at the handshake with no stale process, and `-headless` fixed it; `bgb_run.py` takes the option from the environment variable `BGB_HF`, default `-hf`.) Since §16.16 the helper can answer any status byte: `PRN_ERR=CMD:N:HEX[,...]` (below).

Pages are collected tile by tile (2 tile rows = `$280` bytes per DATA packet, 20 tiles per row) and written as PNG when PRINT arrives, with the palette byte of PRINT (`$E4` in every capture here); every packet is logged (`printer_log.json`: command, length, checksum check, reply, PRINT parameters).

`tools/bgb_print_run.py CORPUS ENTRY ROM OUTDIR [--sav NAME] [--cut N] [--ins N:KEYS:h:w,…] [--seq KEYS:h:w,…] [--tail FRAMES] [--port N]` replays a corpus lineage in BGB with the helper attached and appends / inserts keys (`--ins 13:Right:4:40` = after the first 13 actions of the lineage; `--cut` truncates it); `tools/print_explore.py` and `tools/album_nav.py` are the core-side explorers that find the keys first (all keys from a state, and the cursor path in the album grid).

### 17.2 Where the print screens are and how a photo number reaches its slot (C)

* Album (mode `$0A`): grid `0A:01` ("どの写真を見ますか?", 3 × 3 cells with the first one a label; the cursor value is `$D5D8`, Right at the end of a page turns the page), photo view `0A:03`, menu `0A:04`, then `0A:07` → **`1C:03`**. Second way in: the main menu's link / print entry (`00:05` → A → `06:01` 「プリント / こうかん」, A → **`1B`** 「GAME BOY Printer: プリント / オプション」, §16.2). On `1B:01` **A** (first item プリント) opens `1C:01` 「どの写真をプリントしますか?」, **Right then A** (second item **オプション**) opens **`1E:01`**, the several-photos screen of 17.5 (BGB, `bgb_print_run.py … --cut 14 --seq Right:8:40,A:8:200` ends in `1E:01`, `A:8:200` alone in `1C:01`; from `1C:01` to `1C:03` was not walked). The route through the album's own photo menu (`0A:04` → `0A:07` → `1C:03`) is the one used for 17.3-17.4.
* **The album works on photo numbers, not slots.** `$D5F3` = photo number − 1 on screen ("R-NN" on the printed card is `$D5F3` + 1, 17.4). `bank 2:$444D` searches the 30-byte vector copied from SRAM `$11B2` to `$D563` (§3) for that number and returns **its position = the physical slot − 1**; `bank 2:$4E5F` then copies the 54 tag bytes `F00-F35` of that slot to `$DA5B-$DA90`. In the test save `unl_CE10238211` the vector is `00 01 02 03 17 16 04 18 05 06 07 0B 0C 08 19 1A 09 0A 0D 0E 0F 1B 10 11 12 13 1C 14 15 1D`: photo number 23 (cursor `$17`) is the tag of **slot 5**, photo number 17 is **slot 24**, photo number 5 is slot 9. (Editing slot 24 changes nothing on the card when the card shows photo number 23 = slot 5: the album-order vector explains it.)

### 17.3 Single-photo print: mode `$1C` (C)

Screen `1C:03` (`screens_single_print_1C.png`): the photo in its frame with **「A プリント / B やめる」** (A print / B quit).

| Key at `1C:03` | Result | Tag |
|---|---|---|
| **A** | `1D:04` (「データ転送中」 = "transferring data", TV with a progress bar) → the job (below) | C (BGB with printer) |
| **B** | back to the photo view `0A:03` | C (core) |
| **Start** | toggles `$D806` bit 0 and shows a **speech-bubble marker** (sprite `$CA`) on the screen: the **comment card option** (17.4) | C (marker in my core; the card printed in BGB) |
| **Select** | `1C:04`; then **Up** `1C:05` = density slider 「うすい / こい」 (light / dark: `wPrintIntensity` `$DAAB`, one step per frame while Left / Right is held, clamped to `$00`-`$7F`, default `$40`; `Mode1C_ReadDensityKeys` `08:4441`; it is the exposure byte of the PRINT packet, 17.10), **Down** `1C:06` = 「フレーム」 with the two buttons 「セレクト」 and 「オマケ」 (cursor `$D674`; A → `1C:09`, a light preview of the frame choice) | C for screens and variables in my core; the effect on the PRINT parameters is code reading (`$DAAB` → exposure byte, **I**) and was not run in BGB |

The job in BGB (`pc_289_start/printer_log.json`): `INIT`, 9 DATA packets of `$280` bytes (18 tile rows = 144 px) plus the empty DATA packet, `PRINT [1 sheet, margins $10, palette $E4, exposure $40]`, INQUIRY polls. One page of 160 × 144 pixels: the photo **inside the frame stored with the photo** (`F54`: the Greek-key border for photo 0, the flower / cat border for photo 1, the 「Pocket Camera / 1998 Nintendo / GAME BOY pocket / Pocket Printer」 border for photos 17 and 23). The margin byte `$10` = 1 line feed before the picture, none after (§2: `D802`).

### 17.4 The comment card (Start option): a second page "Camera コメント" (C)

With **Start** pressed before A the job is **two PRINT commands** (`8:45E0` runs pass 1, then `8:46A3` the second job when `$D806` bit 0 is set, §2 `D806`): page 1 as above with margins `$10`, then page 2 with margins **`$13`** (1 line before, 3 after: the card follows the photo almost directly). Page 2 is **not** a photo: `8:46A3` loads graphics from bank `$1B`, calls nine layout routines of bank 9 (`9:45B0 … 9:4775`) which draw a card from the tag buffer, reads the page back from VRAM into `$C000-$CEFF` and sends it (`$DB6D` = 4 for this page). That is the "picture plus the picture comment section" print.

### 17.5 Printing several photos: mode `$1E` (C)

The **オプション** item of the print menu `$1B` opens screen 「OPTION」 (`screens_multi_print_1E.png`): 「FEED かんかく」 with a number of lines (`$D807`, Left / Right, default 3, values 1-5 seen, `1E:01`), the film strip with a pointer on 30 frames (`1E:02`: **A** marks or unmarks the photo under the pointer (bit set in `$D808-$D80F`, bit 7 of `$D808` = photo 0), Left / Right move the pointer `$D810`; the counter 「ごうけい n PHOTOS」 and the 「FILM NO. nn」 label follow), the button 「プリント」 (**Down** from the strip, `1E:03`), 「B…やめる」. **A** on the button starts the job (`1D:04`).

BGB with the helper, photos 0, 1, 2 marked (`pc_927_multi3`): **three PRINT commands, one page of 160 × 144 each**, each with the border stored with its photo (Greek key, flower / cat, Pocket-Printer frame): margins **`$13`, `$03`, `$03`**, i.e. the first photo gets 1 line before and the feed after, the next ones only the feed (3 lines = `$D807`), the last one the feed too (the code of `8:4B32` forces 3 on the last photo, §2 `D802`). No card and no index sheet are printed in this mode. (Only this one selection was run in BGB; marking further photos, unmarking, and the other feed values were checked in my core only, not on paper.)

### 17.7 Coverage re-trace in BGB: how much of what my core saw does BGB reproduce?

**Method (C).** Phase 1, `tools/bgb_trace_core.py`: every entry of a replayable corpus (root save + joypad actions, §13) is replayed depth-first in my core and the **basic-block heads** (`tools/blocks.py`: 15,673 heads covering the 60,449 traced instructions; a head is a jump / call target or the instruction after a branch) it executes for the first time are recorded, so each head has **one witness entry** (a corpus entry with a RAM poke or flagged `tainted` is *forced* and skipped, with its descendants). `tools/bgb_trace_plan.py` keeps one witness per head over the nine corpora (the organic corpus `f1_organic` and the eight fuzz corpora of `coverage/results/corpus/`, which replay to about the same coverage as when they were recorded); `tools/dj_corpus.py` adds a tenth corpus aimed at the music editor (below). Phase 2, `tools/bgb_trace_run.py`: the witness lineage is replayed in BGB as a demo, in plain **Game Boy mode** (`-setting SystemMode=0`, 3 boot frames more than my core, §16.6) with one **logging breakpoint** per witness head (`-br ADDR///ADDR`: BGB writes the address to its debug-message file and goes on), a second set on the 814-877 heads that no core run executed, thinning of hot heads (`..N`), resumable JSONL results, two workers. A head counts as **confirmed** when BGB logs it.

### 17.8 The page layouts of the print job: the scripts at `08:552E-723D` and the progress packets at `08:54DE` (C)

The printer is fed band by band (one band = 2 tile rows × 20 tiles = 40 tiles = 640 bytes, 9 bands = the 144 lines of a screen). What goes into a band is not built by a screen routine: it is described by a **layout script** in bank `$08`, a list of two-byte descriptors {byte 0, flags}, one per tile.

* **How it is read (C).** `00:3118` (print state 3) takes the word `Mode1D_LayoutScriptPtrs[$DB6D]` (`00:32E8`: `552E 57FE 5CAE 656E 6F6E`), adds the byte offset `$DBC0` (+$50 per band) and copies 40 descriptors from bank 8 to `$DB70` (`00:3214`); `00:3161` then renders them into the band buffer `$CF00` and `00:32F2` sends it. For each descriptor: flags bits 0-1 choose an entry of the source table `$DB4D` ({lo, hi, bank}: the photo in SRAM, the info page at `$C000`, or one of the three 2 KiB chunks of a wild-frame page, §16.13), byte 0 × 16 is the offset of the 8 × 8 tile in that source (an absent photo, bank `$FF`, gives a blank tile); bit 6 = blank tile; bit 4 = the tile is turned by 90° clockwise (`00:3249`, the 8 × 8 bit matrix is transposed: out(x,y) = in(y,7-x), simulated); bit 5 = double indirection (byte 0 is a plain byte offset, the byte found there in source k is the tile number and the graphics come from source k of the second table `$DB5D`; layout 0 uses it for its border); bit 7 = last band of the printer page (`$DBC6`); bit 3 = last page of the job (`$DBC5`, bottom margin).
* **The five scripts (C for the bytes and the flags; the page pictures are I, no script was rendered with real sources).** Each photo page uses every photo tile `$00-$DF` exactly once, each frame tile exactly once, and the page lengths agree with the per-page progress words of `Mode1D_ProgressTbl` (`00:30F9`: step × bands = 819, 819, 819, 816, 819).

| `$DB6D` | script | size | printer pages × bands | content |
|---|---|---|---|---|
| 0 | `Print_Layout0_Plain` `08:552E` | 720 B | 1 × 9 | 20 × 18 tiles: 16 × 14 photo tiles in rows 2-15, the 136 border tiles (flags `$21`, indirect) around them |

### 17.10 What the printer's own firmware says (cross-check with the Game Boy Printer disassembly)

The owner's [Game-Boy-Printer-disassembly](https://github.com/Raphael-Boichot/Game-Boy-Printer-disassembly) (commit `facfd6d`, 2026-10-26) reads the printer's mask ROM (Toshiba TMP87C840, md5 `aa393ec87ccb4220200255ab5adf8ac9`) and runs it in a TLCS-870 emulator; its `Printer_protocol.md` is the other side of the camera's print code. Its findings are **C** for the printer (code read and reproduced in its emulator, not yet on a real printer); what they imply for the camera is tagged here.

* **The reply bytes.** The printer answers `0x81` then the status in the two exchanges after the checksum, and `0x00` to every other byte. The camera stores the first in `wPrnDevId` (`$DC28`) and goes on only with `$81` (17.8, `00:30AB`). Until its mechanism has homed (about 1.2 s after power-on), and for ever when the battery or the head temperature is out of range at power-on, the printer answers **`0xFF` to every byte** and never reports `0x80` / `0x40` (printer doc §9): the camera then reads `$FF`, not `$81`, i.e. no printer (**I**: the camera side of that path was not run).
* **Status bits the camera tests after a DATA packet** (`Prn_SendData` `00:1A51-1ABD`, **C** for the camera code): `0x10` packet error -> abort (`Prn_SendData_Abort`, `wPrnAbort`); `0x02` busy -> the same band is queued again from the same pointer, without counting it: right, since the firmware discards any data that arrives while it prints (rollback, printer doc §7); `0x01` checksum error -> the band is not counted and the pointer still moves on by `$0280`.
* **The checksum-error path is not a typo (the open question of §12).** The firmware builds the status byte *before* it compares the checksum, so bit `0x01` arrives **one packet late**, and it rolls back the bad packet at once (printer doc §4, §7; reproduced: `00 01 00`). When the camera sees `0x01` in the reply to band N+1, band N is already gone and band N+1 is stored: not counting the packet and moving on sends one band more at the end; resending the same pointer would have resent band N+1, not N. With this printer no retry can recover band N; the camera's choice keeps the number of bands sent equal to the page height (**I**: the effect on a real print is untested).
* **The empty DATA packet is required.** The firmware refuses PRINT (packet error `0x10`, nothing printed) unless an empty DATA packet came first, and refuses a second one. The camera sends exactly one, flagged by `$DC3D` (`prn_last_chunk`, the end-of-data packet at `00:1C49`).
* **PRINT arguments.** Byte 0 sheets (the camera sends 1; 0 = feed only). Byte 1 margins: high nibble = feed before, low nibble = feed after, in revolutions of the mechanism's cam (the length of one revolution is still open on the printer side): the camera's `$10`, `$13`, `$03` (17.3-17.5) are 1 before / 0 after, 1 before / 3 after, 0 before / 3 after. Byte 2 palette: the camera sends `$E4`, the identity (`$00` means the same). Byte 3 exposure: the firmware accepts `$00-$7F` (above, it uses `$40`) and maps it through the table at `CFF6` to a head on-time offset of **−16 at `$00`, −7 at `$40`, 0 at `$74-$7B`, +1 at `$7C-$7F`**; the camera's density slider covers exactly that range with the same default `$40` (17.3), so "うすい / こい" spans the printer's whole range.
* **Timing the camera must keep.** Inter-byte gap inside a packet: at most 5.12 ms, or the packet is dropped. Silence while not printing: after about 125 ms the printer clears everything, as an Init would, so the camera must not pause between the last DATA and PRINT. Busy (`0x02`) appears 26 ms after PRINT and lasts the whole job (about 9.9 s for nine bands), after which `0x04` stays until the next Init or the idle reset (printer doc §3, §6, §9).
* **What this means for the BGB helper (17.1).** `tools/bgb_printer.py` models the replies from the owner's Arduino captures and differs from the firmware in four points: it reports `0x01` in the same reply (the firmware one packet late) and keeps the flagged band; it answers `0x06` at once after PRINT (the firmware sets busy 26 ms later); it drops to `0x00` after the job (the firmware keeps `0x04` until Init or 125 ms of silence); it does not check for the empty DATA packet. None of these changes the runs of this section, which never flagged a checksum; the `PRN_ERR` runs of §16.16 inject the status byte directly.
