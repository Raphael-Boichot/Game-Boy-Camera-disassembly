## 1. Toolchain, reassembly procedure and disassembly status

### 1.1 Toolchain and reassembly procedure

```
rgbds v1.0.4  (rgbasm/rgblink/rgbfix)  — installed, matches what mgbdis's Makefile expects
mgbdis master — github.com/mattcurrie/mgbdis, commit 95d951a (after the v3.0 tag: the `.data:LEN:WIDTH` row width and `.padding` blocks are not in v3.0), used for the static disassembly pass
```

Procedure (byte-exact, verified working). mgbdis v3.0 has no `--sym` option: it reads `<rom basename>.sym` from the folder of the ROM, so the symbol file must sit beside `pocketcamera_jp.gb` under that name:

```bash
cp roms/jp_rev_a/pocketcamera_jp.sym /path/to/rom/folder/            # beside pocketcamera_jp.gb
python3 mgbdis.py --output-dir disasm_labeled pocketcamera_jp.gb
cd disasm_labeled
make            # runs rgbasm -> rgblink -> rgbfix -> md5sum
# md5sum must print fdcfe686cf4df461e870b6e53b2b5a8b
```

Optional readability pass (does not change a byte, checked by the same md5): `python3 mgbdis.py --print-hex --output-dir out pocketcamera_jp.gb && python3 tools/sym_fix.py out --tables --const && (cd out && make)`. mgbdis v3.0 prints a label for *any* 16-bit operand equal to the address of a label of the current bank (or of bank 0 below `$4000`), whatever the operand means (`ld bc, Label` for a byte count, `ld [Label], a` for an MBC register write, a far pointer read in the wrong bank, a word table as `db $lo, $hi`). `tools/sym_fix.py` rewrites the cases that the code itself decides (74 MBC writes, 28 byte counts and 3 sprite positions in `bc`, 39 far-pointer loads, 1,762 + 246 word-table rows as `dw`, 259 `{lo,hi,bank}` rows as `dw Label` + `db BANK(Label)`); what is left of the artefact is cosmetic (a number printed as the label that happens to share its value). `--ram` and `--const` are the L4 steps: `--ram` writes every WRAM / HRAM operand with its name from `roms/jp_rev_a/disasm/ram_names_jp.csv` and adds `roms/jp_rev_a/disasm/ram_jp.inc` to the listing (§2.13); `--const` (it implies `--ram`) writes the modes, key masks and hardware flags as constants from `roms/jp_rev_a/disasm/const_names_jp.csv` (§2.14). Without them the listing keeps the raw `[$D5CE]` and `ld a, $19`.

#### 1.1.1 The complete symbol file (`pocketcamera_jp.sym`, `disasm/sym_*_jp.csv`)

`pocketcamera_jp.sym` now covers **every byte of the 1 MiB ROM**: 5,349 labels and 7,563 lines in mgbdis v3.0 syntax (`BB:AAAA Name`, plus the block types `.code:LEN`, `.data:LEN[:WIDTH]`, `.text:LEN`, `.padding:LEN`).
Bytes by type: code 117,627 (the 60,449 instructions of the trace, so every `.code` block starts on a proven instruction and the disassembler agrees with the trace on every boundary), data 861,440 (with a row width per structure: 2 for word tables, 3 for `{lo,hi,bank}` far pointers, 32 for tile maps, 16 for tiles), padding 69,494 (2,187 B less than before the L3 pass: fill that sat inside tile tables and maps is typed with its table now, and since 2026-11-01 only runs of $00 are padding, runs of $FF are data), text 15 (`MAIN PASS` at `00:2E88` and the SRAM check string `Magic` at `02:4000`).
It is **generated, not hand-edited**: `tools/sym_build.py` builds it from two layered tables,
`roms/jp_rev_a/disasm/sym_names_jp.csv` (`bank,addr,name,conf,note,source`: later layers win: assets < auto < hand < fixes) and `roms/jp_rev_a/disasm/sym_types_jp.csv` (the block rows), and the trace `roms/jp_rev_a/trace/trace_jp.json`:

```bash
python3 tools/sym_build.py pocketcamera_jp.gb --names roms/jp_rev_a/disasm/sym_names_jp.csv --types roms/jp_rev_a/disasm/sym_types_jp.csv --trace roms/jp_rev_a/trace/trace_jp.json --out pocketcamera_jp.sym --report
```

To rename or retype something, edit a row of the two CSV files and rebuild; the builder refuses duplicate names, a label inside an instruction, a hole or overlap between blocks, and a `.padding` block that is not one repeated byte.

### 1.2 Disassembly status: what is proven, and what is lacking for a confident disassembly

**Byte identity is not the problem.** `mgbdis` + `rgbasm` already reassemble the whole ROM to the exact md5 above, because every byte it cannot type is emitted as `db`.
The open work is *confidence in the classification*: which bytes are code, which are tables / strings / tiles / song streams, and what to call them. That is measured with a
recursive-descent tracer, `tools/rom_trace.py` (v2: `--roots roms/jp_rev_a/trace/extra_roots_jp.json`; without `--roots` it reproduces the first version bit for bit; its symbol input is `roms/jp_rev_a/trace/rom_trace_labels_jp.sym`, the 183 labels of the first pass, because the tracer takes every non-`.data` name as a code root; `python3 -I tools/rom_trace.py pocketcamera_jp.gb roms/jp_rev_a/trace/rom_trace_labels_jp.sym OUT.json --roots roms/jp_rev_a/trace/extra_roots_jp.json` writes `roms/jp_rev_a/trace/trace_jp.json` exactly). ### 1.4 The source tree (L5)

`roms/jp_rev_a/src/` is the editable source of the Japanese Rev A ROM: 64 bank files, 899 `INCBIN` files (675,352 bytes; 494 tile blocks as PNG), 4,912 label notes, 837 far pointers written as labels (13 left as numbers). `make` builds `build/jp_rev_a/pocketcamera_jp.gb` and `make check` compares its md5 with `fdcfe686cf4df461e870b6e53b2b5a8b` (rgbds 1.0.4 in `PATH`, or `RGBDS=/path/`).

* `game.asm` includes `hardware.inc`, `ram_jp.inc` (RAM names, §2.13), `const_jp.inc` (modes, states, keys, hardware flags, sound ids, §2.14), `charmap_jp.inc` (the `kana` charmap, §16.27), then `bank_000.asm` ... `bank_03f.asm`, one `SECTION` per bank.
* Every label of `roms/jp_rev_a/disasm/sym_names_jp.csv` carries its tag (C / I / ?) and its note as a comment (notes cut at 300 characters; the CSV has the full text); every instruction keeps its ROM address as `; $XXXX`.
* `data/bank_BB/`: every block named as tiles, a map or a font, and every other block of plain bytes of 256 bytes or more, is a file: `.png` for tile blocks (16 tiles wide, 4 grays; `gfx.mk` converts them with `rgbgfx`, and `-x` drops the blank tiles that complete the last row), `.tilemap` for tile maps, `.bin` for the rest. `tools/make_source.py` checks that each PNG gives the ROM bytes back.
* A bank number and address handed to a far routine (`Mem_CopyFromBank`, `Vram_CopyFromBank*`, `Far_Call`, `Sgb_Send*`, `SpaceFever_CopyTextRows`) is written `ld a, BANK(Label)` / `ld hl, Label`, so the target can move.
* `macros.inc` holds the macros, each assembling to the bytes it replaces, written on adjacent lines only (no label can sit inside one): `farcopy` (658), `farcall` (276), `dwb` (259), `set_state` (406), `next_state` (185), `play_sfx1` / `play_sfx3` / `play_sfx4` / `play_music` (434), `ui_sfx` (80), `screen_off` (130), `stat_irq_off` (59) and `screen_on` (65); 10 unrolled copies are `REPT` blocks (1,161 lines). `farcopy ROUTINE, SOURCE, DEST, LENGTH` is the bank / source / destination / length set-up and the call of `Mem_CopyFromBank`, `Vram_CopyFromBank`, `Vram_CopyFromBankAuto` or `Vram_CopyFromBank_4`; `farcall TARGET` calls through `Far_Call`; `dwb LABEL` is a `{lo, hi, bank}` pointer row; `set_state STATE` stores a `STATE_*` constant in `wState` (A keeps it); `next_state` is `ld hl, wState` / `inc [hl]` (HL keeps `wState`); `play_sfx1 ID` (and the other channels) is `push af` / `ld a, ID` / `call Snd_Sfx1` / `pop af`; `ui_sfx V` is the same around a store to `wUiSfxRequest`; `screen_off` is `call Pal_FadeOut` / `call Lcd_Off`; `stat_irq_off` clears bit 6 (LY=LYC source) of `hStatShadow` and bit 1 (STAT) of `rIE` (HL ends on `rIE`); `screen_on` is `call Oam_ClearShadow` / `call Pal_AllWhite` / `call Lcd_On`; a `REPT N` block is N copies of `ld a, [hl+]` / `ld [de], a` / `inc e`. Not made macros: the palette set-up and the `bc`-from-table lookup (they would hide which registers end up loaded) and anything used fewer than about 40 times.
* **ROM addresses.** `tools/rom_operands.py` (run by `make_source.py`) classifies every 16-bit operand and table word that looks like a ROM address (`$0100-$7FFF`), every ROM byte read by its address, every table page loaded into a high-byte register and the pointers stored inside data records, and writes the pointers as labels (`Label` or `Label + $off`, `BANK(Label)` for the bank that goes with it): 362 pointers written as labels (111 of them table words), 853 numbers and 108 undecided; 205 pointer words inside data records (169 of them with their bank byte), 7 labels added at code targets and 10 page-aligned tables. Every decision, with its evidence, is a row of `roms/jp_rev_a/disasm/rom_operands_jp.csv` (generated); the cases read by hand are `roms/jp_rev_a/disasm/rom_operands_manual_jp.csv` (two rows). How a value is decided: a short static walk follows the register (copies, push / pop, calls two deep, both sides of a branch, jump tables) to a dereference (a pointer of the mapped bank: the code's bank, the bank written to the MBC on the way, or for bank-0 code the bank the core's runs saw that instruction read), to a routine that takes a bank and an address (`Mem_CopyFromBank`, `Vram_CopyFromBank*`, `Far_Call`, `Far_Call_Return`, `Vq_Push`, `Glyph_LoadFromCharCode`, `Sgb_Send*`, `SpaceFever_CopyTextRows`), to a store through it (a RAM / VRAM address, not a ROM pointer: `ld hl, $7700` + tile x 16 at 04:50C4), or to arithmetic on its bytes (a number: sprite positions, lengths). Pointers inside data records come from the runs: the bytes that each two-read idiom (`ld a, [hl+]` / `ld h, [hl]`, `ld c, [hl]` / `inc hl` / `ld b, [hl]`, ...) read in `cov.npz`, when the pair is then used as an address; then the other records of the same table at its stride, the blit descriptors (5 or 8 bytes), the parlor page lists, and the tables whose label note documents `{... lo; hi; bank ...}` records. The 256-byte tables of the camera effects (`0A:7300-7AFF`) and of the blitter (`00:3700`, `00:3800`) are read with the page in H / B / D: they are written `HIGH(Table)` and carry `ASSERT LOW(Table) == 0`. The 115 undecided are lengths and counts (`$0E00`, `$0140`, `$01C0` ...) and 48 byte pairs typed as words (tile ids, glyph codes); none is read as an address.
* **Relocation test** (`tools/relocation_test.py`, result in `roms/jp_rev_a/disasm/relocation_test_jp.csv`). It moves the content of the banks by 16 bytes (256 for bank 0A, whose tables are page-aligned; bank 0 from `$0150` to the zero fill at `$356C`) taking the bytes from the end padding, rebuilds, replays the 2,835 entries of the organic corpus in the project's core and compares at the end of every entry VRAM, OAM, the LCD registers and the mode / state. With the 29 banks that have room moved at once, 2,800 entries are identical and 35 differ; all 35 come from bank 2A alone, and with `Glyph_LoadFromCharCode` patched to return on code 0 in both builds bank 2A passes all 35: the difference is the original program's own read (below), not a pointer left as a number. Not covered: the 35 full banks (`01 02 0C-0F 11 13 15 16 17 19 1A 1C-25 28 31-33 36-3D`, no 16 bytes of end padding), code that no run of the corpus reaches, and the sound (the screen is compared; the frequency table was fixed by reading).
* **What the ROM itself does with addresses** (found by the test; the source keeps it as it is): `Glyph_LoadFromCharCode` reads 32 bytes at font + (code - 1) x 32, so a code 0 reads `2A:7FE0-7FFF`, the last bytes of the bank (zeros): moved up, that read crosses `$7FFF`. `Parlor_AnimateB` indexes the 2-entry `Parlor_AnimateB_PtrTbl7372` past its end on parlor page 2 and reads bytes of `Parlor_PageTbl` as a map pointer. `Main_Entry` copies 20 bytes from the 17-byte `Main_Entry_Tbl5573` to `wCategoryPosA`: the start positions of categories 17-19 are the first bytes of `Stamp_PaletteInput_Tbl5584` (its first pointer). Sprite ids past the end of `OamPtrTbl_B01_4000` read the list data that follows as pointers. A move that changes those neighbouring bytes changes what the game does there.
* **Listing errors found on the way** (the bytes were right, the names were not): the printer sync bytes `Prn_SyncBytes` (`$88 $33`) and four sound frequencies of `Snd_FreqTbl` were written as the bank-0 labels that sit at those values; ten labels of the wrong bank (`ScrollEngine_Step` at 09:4000 for the font at 2A:4000, ...); the VRAM base `$7700` written as a ROM label; seven absolute reads `ld a, [$5B8A]` ... and the 20 far pointers of the pen blit descriptors left as numbers.
* `make source ROM=pocketcamera_jp.gb [MGBDIS=...]` regenerates the whole tree from the tables of `roms/jp_rev_a/disasm/` and **overwrites hand edits**. The project keeps the tables as the master copy and regenerates; the checker (`--roundtrip`) fails when `src/` is not what `make_source.py` writes or does not build byte-exact. Someone who edits `src/` by hand stops regenerating.

### 1.5 The international ROM: symbol file ported from the Japanese one

The international ROM (`42d2f65e2549be9d1d126a6828b5d1c1`, folder `roms/us_eu/`) differs from the Japanese one in 44.5 % of its bytes, but mostly by whole blocks moved by a fixed offset (relocated addresses, see §16.1), not by rewritten code: masked for their 16-bit address operands, 1,465 of the 2,323 Japanese code labels occur exactly once in the same bank of the international ROM, in only 74 (bank, shift) blocks. So the international symbol file is **carried over from the Japanese tables** instead of being rebuilt from nothing. `tools/port_build.py JP.gb gbcam_us.gb --mgbdis mgbdis.py` reruns every step (under a minute):

1. `tools/port_map.py`: a byte map Japanese -> international, bank by bank. The address operands of the traced instructions and the word tables are wildcards; the candidate shifts come from unique matches of the labels and of 24-byte windows; a Viterbi pass chooses for every byte a shift or a deletion (a lower shift only through a deletion at least as long as the drop, so the order of both ROMs is kept); a deletion facing an insertion of the same length is a replaced block, mapped 1:1.
2. `tools/port_trace_config.py` carries the tracer's Japanese addresses (far call `$08C1` -> `$0956`, one-way far jump `$08BB` -> `$0950`, mode table `$2F3F` -> `$3041`, the dispatch tables, the 23 hand-resolved `jp hl` sites), its roots and its first-pass labels through the map, each code address only where the opcode is the same. `tools/rom_trace.py --config` then traces the international ROM itself: 60,754 instructions (118,153 code bytes), 279 far calls resolved, **0 unresolved** indirect jumps (L2 static; no coverage run on this ROM yet). With no `--config` the tracer still writes `trace_jp.json` bit for bit.
3. `tools/port_code_map.py` aligns the two instruction lists of each bank (difflib, address operands masked): 60,028 of the 60,449 Japanese instructions pair with an international one (53,213 identical, 6,702 with another address operand, 113 with another 8-bit operand). This, not the byte map, places the code names: inside rewritten routines the byte map can be off by a few bytes.
4. `tools/port_syms.py` writes the port layer, `roms/us_eu/disasm/layers/sym_names_us_port.csv` and `sym_types_us_port.csv` (the later layers and the final tables `disasm/sym_names_us.csv` / `sym_types_us.csv`: `HOWTO_NEW_ROM.md` section 0.1). A name keeps its Japanese tag only when its routine is the same code (every instruction up to the next label paired as identical or address-only) or its bytes are identical; otherwise it is tagged I with the reason in `source`. An address written in a name (`Gfx_BB_AAAA_...`, `_Tbl2FB5`, `_B02_6E4B`) is rewritten to the new address of that label. Code evidence then corrects the byte map for data: a data name goes where the paired instructions that load its Japanese address point here, when they all agree (16 names, e.g. `Stamp_PageStrideJmpTbl` at `04:55C7`, 4 bytes from where the bytes put it); a handler name of a Japanese `rst $18` state table goes to the same entry of the international table when both have the same length (1 name: `Mode13_State01_MusicSelect` starts 259 bytes earlier here, with an extra sprite call); the target names of a Japanese word table whose words all point at labels go to the targets of the international table when it was carried whole (70 tables, 126 names moved, 21 lost names found again: mostly the OAM lists, which the bytes alone put on look-alike lists); a Japanese type row follows its moved name, cut at the first traced instruction (18 rows). One name per address: a name placed by code evidence wins, the other is listed as lost. A name placed by code evidence keeps its tag where its bytes are the same here. A name the maps cannot place is searched by its own bytes in its bank (4 found, moved blocks). Every `rst $18` table is typed with the length the international trace gives it. The port layer carries 5,301 names (C 4,037 / I 1,264) and 2,036 type rows; 44 Japanese names were not carried. Hand corrections live in `roms/us_eu/disasm/layers/sym_names_us_hand.csv` (473 rows, applied last, kept when the port is rerun). `tools/port_assets.py` adds the blocks that the international copy calls load (bank, source, length and destination constant on the straight line before a call of `Mem_CopyFromBank`, `Vram_CopyFromBank` and their variants, the last writer of each register being an immediate load): 392 of them start on a carried name, which checks the port independently; the loader layer names the other 28 (`Gfx_` / `Map_` / `Src_` + consumer, tag C) with their type rows, in `layers/sym_names_us_loaders.csv` / `layers/sym_types_us_loaders.csv` (layers: carried < loaders < hand).
5. `tools/sym_build.py` writes `roms/us_eu/gbcam_us.sym` (7,698 lines); mgbdis + rgbasm rebuild the ROM byte for byte, plain and after `sym_fix.py --tables --far-helpers 0473,049C,061B,068D,0734,0950,0956` (the banked helpers at their international addresses).

*L3, read sites and the last tables (2026-11-02).*

**The core's read sites were wrong after interrupts** (`coverage/src/gbcov.c`). A read's site is the call that selected its bank. When the VBlank interrupt switched banks in the middle of a far copy and switched back, every later read of the copy was credited to `Irq_VBlank`; reads made after the selecting routine had returned kept its site too. Two fixes:
* the site is saved at each interrupt and restored at `reti`;
* a read with a stack pointer above the one of the bank switch records no site.

The core can also record the routine that queued a VBlank copy (`GBCAM_QPC`) and the reader's call chain (`GBCAM_RCHAIN`). `tools/port_queue_origin.py` replays a corpus with them. The VBlank queue turned out to copy none of the open blocks.

**Reached on a patched copy (forced, 2026-11-02):** the final `ret` of `LinkPick_RequestRemotePage` (`07:516D`, 1 B). It runs when a receiving unit that browses the partner's album gets its thumbnail page before the 180-frame deadline (`wLnkHalfDone`). Between two BGB instances that page always arrives late, as in Japan: eleven exchanges and four receiver-initiated ones on the plain ROM end on message `$0C` (`0E:14`). Timed in BGB on 2026-11-02 (breakpoints at the request `07:5146` and at `07:516D`, frames counted at the VBlank vector): the first page arrives 201 frames after the request and a second page, asked for by paging with the receiver's D-pad, after 207, against a deadline of 180; on the plain ROM the time-out fires at frame 179. A page is 2,055 exchanges of about 5,980 cycles (§14.2), about 175 frames on the wire alone, so the clock rates and the code, not the emulator, make it late: the branch is unreachable on hardware too (README: the Game Genie codes `00A-8BB-3AE`, Japanese `00A-CEB-3AE`). So, as the owner did for the Japanese ROM, the deadline is switched off in a copy of the ROM: one byte, `07:4A8B` `dec [hl]` -> `nop` in `Link_TimeoutTick` (the copy is not committed; make it by changing file offset `$1CA8B` from `$35` to `$00`).
