## 1. Toolchain, reassembly procedure and disassembly status

### 1.1 Toolchain and reassembly procedure

```
rgbds v1.0.4  (rgbasm/rgblink/rgbfix)  — installed, matches what mgbdis's Makefile expects
mgbdis master — github.com/mattcurrie/mgbdis, commit 95d951a (after the v3.0 tag: the `.data:LEN:WIDTH` row width and `.padding` blocks are not in v3.0), used for the static disassembly pass
```

Procedure (byte-exact, verified working). mgbdis v3.0 has no `--sym` option: it reads `<rom basename>.sym` from the folder of the ROM, so the symbol file must sit beside `pocketcamera_jp.gb` under that name:

```bash
cp roms/jp_rev_a/pocketcamera_jp.sym /path/to/rom/folder/            # beside pocketcamera_jp.gb
python3 mgbdis.py --output-dir disasm_labeled pocketcamera_jp.gb
cd disasm_labeled
make            # runs rgbasm -> rgblink -> rgbfix -> md5sum
# md5sum must print fdcfe686cf4df461e870b6e53b2b5a8b
```

Optional readability pass (does not change a byte, checked by the same md5): `python3 mgbdis.py --print-hex --output-dir out pocketcamera_jp.gb && python3 tools/sym_fix.py out --tables --const && (cd out && make)`. mgbdis v3.0 prints a label for *any* 16-bit operand equal to the address of a label of the current bank (or of bank 0 below `$4000`), whatever the operand means (`ld bc, Label` for a byte count, `ld [Label], a` for an MBC register write, a far pointer read in the wrong bank, a word table as `db $lo, $hi`). `tools/sym_fix.py` rewrites the cases that the code itself decides (74 MBC writes, 28 byte counts and 3 sprite positions in `bc`, 39 far-pointer loads, 1,762 + 276 word-table rows as `dw`, 259 `{lo,hi,bank}` rows as `dw Label` + `db BANK(Label)`); what is left of the artefact is cosmetic (a number printed as the label that happens to share its value). `--ram` and `--const` are the L4 steps: `--ram` writes every WRAM / HRAM operand with its name from `roms/jp_rev_a/disasm/ram_names_jp.csv` and adds `roms/jp_rev_a/disasm/ram_jp.inc` to the listing (§2.13); `--const` (it implies `--ram`) writes the modes, key masks and hardware flags as constants from `roms/jp_rev_a/disasm/const_names_jp.csv` (§2.14). Without them the listing keeps the raw `[$D5CE]` and `ld a, $19`.

#### 1.1.1 The complete symbol file (`pocketcamera_jp.sym`, `disasm/sym_*_jp.csv`)

`pocketcamera_jp.sym` now covers **every byte of the 1 MiB ROM**: 5,347 labels and 7,563 lines in mgbdis v3.0 syntax (`BB:AAAA Name`, plus the block types `.code:LEN`, `.data:LEN[:WIDTH]`, `.text:LEN`, `.padding:LEN`).
Bytes by type: code 117,627 (the 60,449 instructions of the trace, so every `.code` block starts on a proven instruction and the disassembler agrees with the trace on every boundary), data 860,295 (with a row width per structure: 2 for word tables, 3 for `{lo,hi,bank}` far pointers, 32 for tile maps, 16 for tiles), padding 70,639 (1,042 B less than before the L3 pass: fill that sat inside tile tables and maps is typed with its table now), text 15 (`MAIN PASS` at `00:2E88` and the SRAM check string `Magic` at `02:4000`).
It is **generated, not hand-edited**: `tools/sym_build.py` builds it from two layered tables,
`roms/jp_rev_a/disasm/sym_names_jp.csv` (`bank,addr,name,conf,note,source`: later layers win: assets < auto < hand < fixes) and `roms/jp_rev_a/disasm/sym_types_jp.csv` (the block rows), and the trace `roms/jp_rev_a/wram/trace_jp_v3.json`:

```bash
python3 tools/sym_build.py pocketcamera_jp.gb --names roms/jp_rev_a/disasm/sym_names_jp.csv --types roms/jp_rev_a/disasm/sym_types_jp.csv --trace roms/jp_rev_a/wram/trace_jp_v3.json --out pocketcamera_jp.sym --report
```

To rename or retype something, edit a row of the two CSV files and rebuild; the builder refuses duplicate names, a label inside an instruction, a hole or overlap between blocks, and a `.padding` block that is not one repeated byte.

Two of them are whole jobs reached by a jump: the print job of the TRIPY-H editor (`DjPrint_Job`, `05:5959`) and the comment-card branch of the print job (`Mode1C_State08_PrintJob_CommentCard`, `08:46A3`). Eleven of the 110 shared an address with a `jr_` label, so the `jr_` count fell from 3,178 to 3,167; the listing has no `Jump_` label left and the md5 round trip is unchanged in the four variants (the checker counts mgbdis' own labels in the plain listing, `auto labels`). These names replace labels that were never in the sym, so `renamed_jp.csv` does not list them. One thing found on the way: mgbdis prints the name of a label of the *current* bank for a far-call operand with the same address, so `ld hl, CommentEditor_DrawTextCursor` at `09:5FDA` is a call to `02:4466` (`Photo_RenumberVector`): the name in the source is bank 9's, the callee is in bank 2 (the listing is right, the label is only the nearest one by address).

### 1.2 Disassembly status: what is proven, and what is lacking for a confident disassembly

**Byte identity is not the problem.** `mgbdis` + `rgbasm` already reassemble the whole ROM to the exact md5 above, because every byte it cannot type is emitted as `db`.
The open work is *confidence in the classification*: which bytes are code, which are tables / strings / tiles / song streams, and what to call them. That is measured with a
recursive-descent tracer, `tools/rom_trace.py` (v2: `--roots tools/extra_roots.json`; without `--roots` it reproduces the first version bit for bit; its symbol input is `tools/rom_trace_labels.sym`, the 183 labels of the first pass, because the tracer takes every non-`.data` name as a code root; `python3 -I tools/rom_trace.py pocketcamera_jp.gb tools/rom_trace_labels.sym OUT.json --roots tools/extra_roots.json` writes `roms/jp_rev_a/wram/trace_jp_v3.json` exactly). A byte is *proven code* only if it lies on a decoded path.

| Trace | Proven instructions | Proven code bytes (banks 00, 02-0A, 1F) | Unresolved indirect jumps |
|---|---:|---:|---:|
| first tracer (vectors, `.sym` labels, mode and state tables) | 56,799 | 111,808 | 14 |
| + 89 live roots and four rules (`jp hl` tables, callbacks, cooperative tasks, soft reset, OAM-DMA stub) | 59,866 | 116,613 | 0 |
| + 45 unreferenced "dead-code" roots (all 134 roots) | 60,449 | 117,627 | 0 |

The 11 code banks hold 180,224 bytes: **117,627 proven code (65 %)**, 1,256 inline jump / mode tables, 2,164 padding, 2,400 unreferenced (2,251 of them `0A:6BDD-74A7`: 1,827 zero bytes plus the popcount table `$7300` and the bit-reverse table `$7400`, both verified), and 56,777 bytes of data of unknown type.
The biggest single gain was the bank `$0A` jump table at `0A:541A` (96 entries, reached through `06:781D → 0A:7CFE`, the first tracer capped it at 32): +2,444 instructions of image-effect code. Indirect flow after the work: 31 `jp hl` (8 by table idiom, 23 by hand or rule), 46 inline `rst $18` tables, 276 far calls (72 distinct targets), 0 unresolved.
All consistency checks pass (no overlapping instructions, every callback ends in `ret`/`jp`, no invalid opcode on a proven path). The 45 dead-code roots decode cleanly but nothing calls them: they are *reachable by decoding*, not proven live.

**What is lacking, by importance**

1. **The data banks are unstructured.** *(Update, §13.5: the emulator run reads all 14 banks that no code references and logs which mode, state and routine reads which range; the type and extent of each asset inside a bank are still open.)* Banks `$0B-$3F` except the sound bank `$1F` (52 banks, 851,968 bytes) are not described: the asset catalog (`roms/jp_rev_a/assets/catalog_jp.csv`, 385 copy sites) accounts for 254,546 bytes (29.9 %). 25 of these banks have no catalogued byte, and **14 banks (`2B 2D 2E 30-35 37 3A-3D`, 229,376 bytes) have no static reference at all** yet hold real content (not padding). They are reached through computed bank numbers and pointer tables that static tracing cannot follow. Until that is solved a source file can only `INCBIN` them, not name sections.
   Bank `$01` is not in these 52: it is the one data bank that is **already fully typed**. It holds the sprite-composition lists drawn by the OAM adders `00:24AF` (pointer table `$4000`, 249 entries) and `00:2496` (pointer table `$5D47`, 246 entries): each pointer leads to 4-byte OAM records (Y, X, tile, attribute) ended by `$80` (3,247 records in all; `A` = list number, `C`/`B` = Y/X offset added to every record, written to the OAM shadow at `$D400 + FF9A`). Parsing both tables covers `$4000-$7888` (14,473 bytes) with no gap; `$7889-$7FFF` (1,911 bytes) is zero padding. Bank `$02` has two more tables of the same kind (`$6E4B` for `00:2464`, `$5272` for `00:247D`), not parsed yet.
2. **About 57 KB of data inside the code banks has no known type or extent** (bank `$02` 11.9 KB, `$1F` sound data 12.3 KB, `$08` 10.0 KB (7,440 B of it are the five print layout scripts of `08:552E`, reached through the word table `00:32E8` and typed since), `$09` 5.3 KB, `$00` 4.1 KB, `$06` 3.4 KB, `$0A` 2.3 KB…): word tables vs strings vs tiles vs song streams. This is an upper bound: `tools/rom_coverage.py` credits a table as referenced when any `ld rr,nn` constant lands near it, and a bank-0 `ld hl,nn` ≥ `$4000` is credited to every bank. The only data of known extent is the 254,344 bytes copied through `call $0450` with a constant length.
3. **Reachable is not live.** 45 roots (1,014 bytes) are unreferenced code (library stubs, an unused sound-effect starter, twin routines `05:7F1C` / `09:721D`…). *(§13.3: in the emulator run none of the 45 executed from joypad input; one ran once in a forced run through an edge that is not in the static control flow, an artefact.)*
4. **Heuristic completeness.** The cooperative-task entries of bank 3 (program counters stored as split immediates `ld a,lo ; ld [$D6FD],a ; …`) and the 23 hand-resolved callbacks come from pattern scans, not from a proof that none is missing. The tracer also had one real bug, fixed in v2: an `rst $18` table at `05:48C4` was read one word too long and swallowed the first instruction of `Bank005_State12` as table data (bytes unchanged, labelling wrong).
5. **Text table.** The ROM holds no other text: its only strings are the ASCII `MAIN PASS` (`00:2E88`) and `Magic` (`02:4000`, the SRAM tag), typed as text; every menu, message, credit and printer text is tile graphics placed by tile maps (a scan for ASCII runs finds only tile-id sequences of maps), and the stamp letters of banks `$2D`, `$2E`, `$30` are stamp graphics. The one character set of the code is the name / comment set (`roms/jp_rev_a/disasm/charset_jp.csv`, 245 codes, §16.27), used for the fields the player types (SRAM and WRAM, not ROM). `tools/charmap_jp.py` writes it as the rgbasm character map `kana` (`roms/jp_rev_a/disasm/charmap_jp.inc`, the default map stays ASCII), and `sym_fix.py --const` writes the only ROM tables in that set with it (`roms/jp_rev_a/disasm/text_tables_jp.csv`): the voiced-mark maps of the keyboard, `Kb_DakutenMapTbl` (`db "か", 15, "が"` ... `db "ハ", 5, "バ"`, 5 records) and `Kb_HandakutenMapTbl` (は / ハ x5 -> ぱ / パ), between `PUSHC kana` and `POPC`; the ROM rebuilds byte-exact. Their decoding (か-と -> が-ど, は-ほ -> ば-ぼ, ウ -> ヴ ...) also confirms the code order of the table. The international character set is not extracted.

**What needs the emulator or the hardware.** *Done:* the coverage run (§13; with the unlocking and link runs of §15.1, 57,582 of the 60,449 traced instructions (95.3 %) executed, 50,008 (82.7 %) from joypad input and an SRAM image alone, **0 executed instructions outside the trace**, none of the 45 dead roots executed from joypad input), the ROM-read log for the 14 unreferenced banks (§13.5), the link partner (§14), Super Game Boy (§16.13), the BGB re-trace of the covered paths (§17.7) and the never-run code (§16.14-§16.21, §16.26: 1,192 B left, all classified). *Still open:* what only hardware or a cycle-exact emulator can settle: the timing of link bytes, sensor-dependent decisions (§18.9), and anything seen or heard on a real camera.

**Choices for a rebuilt source:** the 45 dead roots are assembled as code tagged unused (owner decision 2026-10-26, §13.6): each carries the `Unused_` prefix. The character table is done (§16.27). Quirks that a rebuilt source must keep bit-exact are real ROM behaviour, e.g. `0A:4C51` is an unconditional `jr` that skips an `inc b` (it looks like a `jr z` that was meant, but the bytes are what they are).

Full report with the per-bank table, the resolved indirect sites and the verdict on the 15 unreferenced regions: `roms/jp_rev_a/disasm/code_gaps.md` and `roms/jp_rev_a/disasm/coverage_jp_v3.csv`. The runtime counterpart (what executes, what never does) is §13 and the package folder `coverage/`.

### 1.4 The source tree (L5)

`roms/jp_rev_a/src/` is the editable source of the Japanese Rev A ROM: 64 bank files, 886 `INCBIN` files (668,189 bytes; 491 tile blocks as PNG), 4,910 label notes, 837 far pointers written as labels (13 left as numbers). `make` builds `build/jp_rev_a/pocketcamera_jp.gb` and `make check` compares its md5 with `fdcfe686cf4df461e870b6e53b2b5a8b` (rgbds 1.0.4 in `PATH`, or `RGBDS=/path/`).

* `game.asm` includes `hardware.inc`, `ram_jp.inc` (RAM names, §2.13), `const_jp.inc` (modes, states, keys, hardware flags, sound ids, §2.14), `charmap_jp.inc` (the `kana` charmap, §16.27), then `bank_000.asm` ... `bank_03f.asm`, one `SECTION` per bank.
* Every label of `roms/jp_rev_a/disasm/sym_names_jp.csv` carries its tag (C / I / ?) and its note as a comment (notes cut at 300 characters; the CSV has the full text); every instruction keeps its ROM address as `; $XXXX`.
* `data/bank_BB/`: every block named as tiles, a map or a font, and every other block of plain bytes of 256 bytes or more, is a file: `.png` for tile blocks (16 tiles wide, 4 grays; `gfx.mk` converts them with `rgbgfx`, and `-x` drops the blank tiles that complete the last row), `.tilemap` for tile maps, `.bin` for the rest. `tools/make_source.py` checks that each PNG gives the ROM bytes back.
* A bank number and address handed to a far routine (`Mem_CopyFromBank`, `Vram_CopyFromBank*`, `Far_Call`, `Sgb_Send*`, `SpaceFever_CopyTextRows`) is written `ld a, BANK(Label)` / `ld hl, Label`, so the target can move.
* `macros.inc` holds the macros, each assembling to the bytes it replaces, written on adjacent lines only (no label can sit inside one): `farcopy` (628), `farcall` (194), `dwb` (259), `set_state` (406), `next_state` (185), `play_sfx1` / `play_sfx3` / `play_sfx4` / `play_music` (434), `ui_sfx` (80), `screen_off` (130), `stat_irq_off` (59) and `screen_on` (65); 10 unrolled copies are `REPT` blocks (1,161 lines). `farcopy ROUTINE, SOURCE, DEST, LENGTH` is the bank / source / destination / length set-up and the call of `Mem_CopyFromBank`, `Vram_CopyFromBank`, `Vram_CopyFromBankAuto` or `Vram_CopyFromBank_4`; `farcall TARGET` calls through `Far_Call`; `dwb LABEL` is a `{lo, hi, bank}` pointer row; `set_state STATE` stores a `STATE_*` constant in `wState` (A keeps it); `next_state` is `ld hl, wState` / `inc [hl]` (HL keeps `wState`); `play_sfx1 ID` (and the other channels) is `push af` / `ld a, ID` / `call Snd_Sfx1` / `pop af`; `ui_sfx V` is the same around a store to `wUiSfxRequest`; `screen_off` is `call Pal_FadeOut` / `call Lcd_Off`; `stat_irq_off` clears bit 6 (LY=LYC source) of `hStatShadow` and bit 1 (STAT) of `rIE` (HL ends on `rIE`); `screen_on` is `call Oam_ClearShadow` / `call Pal_AllWhite` / `call Lcd_On`; a `REPT N` block is N copies of `ld a, [hl+]` / `ld [de], a` / `inc e`. Not made macros: the palette set-up and the `bc`-from-table lookup (they would hide which registers end up loaded) and anything used fewer than about 40 times.
* Limits: about 390 operands or table words in `$4000-$7FFF` are still numbers (some are pointers, some counts), so growing a block can still break code that points past it: rebuild and compare, or check those operands first.
* `make source ROM=pocketcamera_jp.gb [MGBDIS=...]` regenerates the whole tree from the tables of `roms/jp_rev_a/disasm/` and **overwrites hand edits**. The project keeps the tables as the master copy and regenerates; the checker (`--roundtrip`) fails when `src/` is not what `make_source.py` writes or does not build byte-exact. Someone who edits `src/` by hand stops regenerating.
