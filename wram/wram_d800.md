## WRAM `$D800-$D9FF` (region `d800`)

*Status: complete pass on the v2 tables. Coverage: all 274 addresses of this range that appear in `wram/wram_summary.csv` have a row: 224 code-traced (C), 47 inferred (I), 2 unused/dead (U: `D818`, `D92E`), 1 inconclusive (?: `D861`). The remaining 238 bytes of the 512-byte page never appear in the summary; they are covered by rows too (C/I/U: array members reached by indexed addressing, padding slots), so the page has no undocumented byte. Rows are in address order; each overlay has its own paragraph.*

### 0. What this page really is

The page is **not** one structure. It is a stack of unrelated overlays that happen to share the addresses:

| Range | What | Mode / bank |
|---|---|---|
| `$D800-$D816` | print job state (`$D801-$D814`), plus three unrelated bytes: `$D800` (launch flag), `$D815` (title scene), `$D816` (bank-3 sprite sweep) | bank 8 modes `$1B/$1C/$1D/$1E`, the margin consumer is in the fixed bank (`0:3339`) |
| `$D818-$D88F` | working set of **mode `$07`** (`7:54ED`): a vertical shoot-'em-up whose first wave is the menu that starts modes `$1F`, `$20`, `$21` | bank 7 |
| `$D890-$D9D6` | **the music ("sound") editor/player** (mode `$1F`) | bank 5 `$4000-$74CB`; playback engine in **bank 0 `$1017-$1560`** (called every frame from bank 5); RAM<->SRAM pack/unpack in **bank 2 `$4A6B` / `$4F2B`** |
| `$D9D7-$D9F7` | mode `$20` (`5:74CC`): a small three-object action game with its own two-row menu | bank 5 `$74CC-$7FFF` |
| `$D9F8-$D9F9` | character pick of mode `$21` (`9:5FE3`) | bank 9 |
| `$D9FA-$D9FF` | four sprite animators of mode `$0E` (`7:4000`, link-cable exchange screen) | bank 7 |

(The Game Boy Camera documentation names its games "Space Fever II", "Ball", "Run! Run! Run!" and the music editor "DJ"; matching them to modes `$07`, `$20`, `$21`, `$1F` is an inference from behaviour, not from text found in the ROM, and is tagged I wherever it appears. The code facts do not depend on it.)

The previous README read `$D890-$D9F8` as "three parallel 3-byte cursor structures of a grid/stamp picker" and `$D9D1-$D9F1` as "per-slot validity flags". **Both are wrong**: the three cursors are the *field cursors of the three channel pages* (SOUND I, SOUND II, NOISE) of the sound editor, `$D9D1` is the **tempo**, `$D9D2` is the "sound saved" flag, `$D9D3/$D9D5/$D9D6` are menu selections of the sound editor's start menu. See "Corrections" at the end.

**The 217-byte settings block is NOT mirrored in WRAM as one block.** The sound part of the SRAM settings block (`$1061-$10BA`, 90 bytes) is *unpacked* into a byte-per-field layout at `$D93D-$D9D2`; the animation list (`$1000-$105E`) is at `$D681-$D6E3` (other region); a flat 22-byte image of `$10BB-$10D0` sits at `$DA96-$DAAB` (other region); the Game Face flag `$10D1` is `$D581`. The base of the sound image and the full field-by-field map are in section 3.1.

### Method and evidence

* Every claim cites `bank:address` of instructions that I read in the linear-sweep listing (`disasm_hex/bank_XXX.asm`) and that belong to the proven-code set (`trace_jp.json` key `code`). "C" rows are code-traced; "I" rows name a role inferred from the data flow; "U" rows are dead/unused in the proven code; "?" rows are inconclusive.
* The tracer's built-in mode table stops at mode `$1D`; the traces used here add the roots `8:4887`, `5:4000`, `5:74CC`, `9:5FE3` (tools/extra_roots.json). The access tables now contain exactly the same 274 addresses for this range as a separate re-trace with those roots (checked: no address on either side only), so the numbers below use these tables.
* Unresolved data-driven callbacks of that trace (bank 3 `$5F68/$5F91`, bank 7 `$792C/$7BF3/$7C62/$7CD1`, `call $FF80`) could touch variables of this page without being visible in the access table; nothing in the code read here suggests they do.
* Names in the "Name" column are mine; sweep labels such as `Call_000_1017` are not names.


### 1. `$D800-$D816` print job state (bank 8, modes `$1B-$1E`), extras-launch flag, title scene, sweep counter

**This block is not a "print settings" structure of 0x36 bytes.** Only `$D801-$D804`, `$D806-$D814` belong to the print flow (bank 8 modes `$1B` `8:4000` print menu, `$1C` `8:40F8` print option screen, `$1D` `0:3015` print engine in the fixed bank, `$1E` `8:4887` photo-selection and margin dialog). `$D800`, `$D805`, `$D815`, `$D816` are unrelated bytes that happen to sit in the same page. Nothing in this block is saved to SRAM; `$D807` is initialised to `3` by the main-loop start (`00:2F1B`), everything else is zero from the boot clear (`00:0181`).

**Print flow (code-traced).** Mode `$1C` (single photo, 14 states, table `8:40FC`): state 0 `8:411A` clears `D806`; state 3 `8:4291` is the option screen where **Start toggles `D806` bit 0** and Select advances; state 7 `8:458D` starts the job (`D803:=0`, `D814:=0`, `D804:=1`); state 8 `8:45E0` is the dispatcher run after every pass: it stops if `D814` != 0, runs pass 1 (`D803` 0 -> 1, builds `DB4D-DB4F` and calls `8:50F6`/`8:540D`, margin per `D806`, then `D5CE:=$1D`), runs pass 2 only if `D806` bit 0 is set (`8:46A3`) and otherwise returns to state 2. Mode `$1E` (print several photos, 6 states, table `8:488B`): state 0 `8:4897` loads the screen; state 1 `8:4913` = margin page (Left/Right on `$FFA3` change `D807`; A or Down -> state 2; B -> state 4 which exits to mode `$1B`); state 2 `8:497F` = photo page (Left/Right on `$FFA9` move `D810`; A on `$FFA8` toggles the photo in `$D808-$D80F`; Down -> 3, Up -> 1, B -> exit); state 3 `8:4A38` = confirm (A -> 4, Up -> 2, B -> exit via 4); state 4 `8:4A7E` exits on B else starts the job (`D803:=0`, `D814:=0`, `D804:=1`); state 5 `8:4AA7` is the loop: for each `D803 < $3C` whose bit is set it prepares the packet source (`DB4D-DB4F` from `2:517B`, `2:4E31`, `8:50F6`), computes the margin byte into `D802`, sets `D801:=1` and hands over to mode `$1D` (print engine, `0:3015`); the engine returns to state 5 which continues with `D803+1`. The fixed-bank packet builder `0:3339-0:3369` consumes `D801/D802` (see rows).

**Margin byte.** `0:3341` starts with `DE=$1003` (default: 1 blank line before the first band, 3 after the last). If `D801 != 0` it uses `D = D802 & $F0` and `E = D802 & $0F` instead. The byte sent in the packet (`DC09`, `0:3369`) is `(D if DBC4 else 0) \| (E if DBC5 else 0)`: the top margin only goes into the first band packet (`DBC4` = first-band flag) and the bottom margin only into the last (`DBC5` = last-band flag). Dialog value `D807` (0..9) is the **bottom margin** of every photo but the last one of the job; the last photo always gets 3 (`8:4B2C-4B2E`); the first photo of the job gets a top margin of 1 (`D804` != 0 -> `B=$10`, `8:4B1F-4B25`).

### 2. `$D818-$D88F` bank-7 mode `$07` (`7:54ED`): shoot-'em-up that doubles as the game-selection screen

**This block is the working set of mode `$07`, a vertical shooter, not a frame/stamp editor.** Mode `$07` (9 states, table `7:54F1`) draws a scrolling star field, a player ship at y=`$88` that moves left/right in steps of 2 (`D819`), fires with A and is hit by enemies and enemy bullets. Its first wave (`D863` = 0/1, `7:59C1`/`7:5A94`) contains **three target enemies that are the menu**: when the enemy whose animation slot `D502`/`D503`/`D504` reaches frame `$0A` is shot (`7:5AFA-5B1F`) the state byte is set to 6, 5 or 7, and states 5, 6, 7 (`7:56C6`, `7:56E4`, `7:5702`) store the hi-score block (`2:4BB2`) and start **mode `$1F` (the sound editor), mode `$20` and mode `$21`**. Later waves (`D863` 2..9) are ordinary shooter waves ending with a boss (`7:620F`); the round counter `D88E` and the boss variant `D88F` advance after each boss. A B press or a hit sets `D88D`. Pausing/continuing uses the two-way cursor `D88B` (Left/Right, states 3 and 4, `7:5756`) bobbing with `D88C`. The game is probably the Game Boy Camera's "Space Fever II" shooter (name from public knowledge, not from ROM text: I).

**Data layout (code-traced).** Per-enemy arrays are indexed by `E = 0..2` (three enemies); player shots use 8 slots (only slots 0-2 are reachable, see `D818`) and enemy bullets 8 slots; the star field has 10 slots. Enemy motion: a 16-bit fixed-point path position `D83B+2E` (low byte = fraction, high byte = index into a table of (dx, dy) byte pairs built into `$CE00 + 2*index` from compressed ROM lists by `7:6557`, e.g. lists at `7:5A39`, `7:5B8B`, `7:6139`), advanced by `2 * D844+E` per frame after the start delay `D860` (`7:6387-63A8`); the enemy position is `D835+E = path_dx + D82F+E` and `D838+E = path_dy + D832+E`, with `D847+E` bit 7 mirroring x (`x := $51 - x`, `7:6400-641A`). An enemy whose index reaches `D841+E` ends its pass (`D85F |= 1 << E`, table `7:641C`). The boss (wave 4, `D863` 9) uses a hit counter `D865` (50 hits) and a collision mask of `$38 x $40` pixels read from `$D000 + 64*D866 + ...` (`7:66E9-6731`); the three 64-byte masks at `$D000/$D040/$D080` are built from the boss graphics by `0:1668` using `D88F` (page `$D000` is outside this region).

### 3. `$D890-$D9D6` sound ("music") editor and player, mode `$1F`

Mode `$1F` = bank 5 `$4000`. States of `$D5CF` (13): 0 init/load; 1-3 start menu; 4 init performance screen; **5 performance screen (plays the tune)**; 6/7 save / exit dialogs; 8 init editor; **9 SOUND I page, 10 SOUND II page, 11 NOISE page**; 12 leave. Within pages 9-11 the field is chosen by the cursor byte (`$D8C8`/`$D8F3`/`$D8FA`) through `rst $18` tables at `5:475F` (12 fields), `5:4806` (10), `5:48C4` (8). Start+A on the editor jumps to `5:5959`, which **prints the tune as a score on the GB Printer** (rows in `$D8C6`, band flags `$D8C7`).

Hardware mapping (proved by the writes in `0:1017-1560`): **SOUND I -> hardware channel 2 (NR21-NR24)**, **SOUND II -> channel 3 (wave, NR30-NR34)**, **NOISE -> channel 4 (NR41-NR44)**; hardware channel 1 (NR10-NR14) is left to the UI sound effects (`$D92E`, see below).

### 4. `$D9D7-$D9FF` mode `$20` mini-game, the character pick of modes `$20`/`$21`, bank-7 link-screen animators

**Mode `$20` (`5:74CC`, state table `5:74D0`, 12 states) is a small action game, not a settings screen.** Entered from mode `$07` (`7:56E9`, state 6 of the shooter menu, at state 0) and from mode `$16` (bank 6, option 1: `6:48B6-48C7` sets `D9F3:=2`, `D890:=$16`, `D5CE:=$20`, `D5CF:=2`, i.e. it skips the menu states) and from its own menu (state 1, `5:756A`). States: 0 `74E8` init (graphics from banks `$1A`/`$24`, BGM `$2C`, cursor `D9EF:=0`); 1 `756A` menu with two rows (`D9EF` = row 0/1 chosen with Up/Down, `D9F2` = row-0 value 0..1, `D9F3` = row-1 value 0..2, both with Left/Right; A starts and stores the caller mode in `D890`, B returns to mode 0); 2 `7774` loads the game graphics (bank `$1D` tiles `$5D00` -> VRAM `$8000`, bank `$22` two tile maps) and enables the STAT-interrupt scroll effect (`FFAC` bit 6, `IE` bit 1, `FFC5 := 5`, `5:77DD-77E9`); 3 `77FC` starts the BGM chosen by `D9F2` (table `5:781B` = `2E 02`, `2D 02` through `0:2A4B`) and initialises the game variables (`5:79F4`); 4 `781F` play (Start -> state 7 pause); 5 `7859` same engine with the joypad replaced by synthetic input from `5:7DCC` (attract/demo; a real key press goes back to state 3); 6 `7886` miss animation; 7 `78F2` pause; 8 `793A` exit (`D890 == $16` -> mode `$16` state 1, else state 0); 9 `7963` loads the end screen (banks `$1B`, `$23`), 10 `79A6` waits for A/B (`D5DF`), 11 `79CA` A = retry (state 2), B = exit as state 8.

**Game logic (code-traced, naming inferred).** Three objects move along fixed step paths (tables `5:7C23`, `5:7C37`, `5:7C4F`, one 16-bit-word pair per step, bit 7 of the first word = hidden entry); their step counters are `D9DB-D9DD`, directions `D9DE-D9E0` (+1 or `$FF`), end limits `8, 10, 12` (`5:7BD3`). A 16-bit accumulator `D9E4:D9E3` gains a speed from table `5:7B6D` each frame (index from the score, see `D9E3`); each carry steps the next object in round-robin order (`D9E5`, sound `$20 + index`). The player has three positions `D9D7` = 0..2 (Left/B decrement, Right/A increment, sound 1); standing at the right position when an object reaches an end (`5:7C6B`) reverses its direction, adds 1 to the BCD score and plays sound `$23`; an object that reaches an end with the wrong position, or goes below 0, ends the game (`5:7B4A`, state 6). It looks like a three-ball juggling game, but the in-game name was not read. The best score (4 BCD digits) lives at `$DAA4` (low) / `$DAA5` (high) and is written to SRAM `$10C9/$10CA` through `2:4BB2` as soon as it is beaten (`5:7E89`); `DAA4/DAA5` are outside this page.

### Corrections to the previous README

README (`$D800-$D835` section and the `$D890-$D9F8` / `$D9D1-$D9F1` rows of the WRAM chapter) versus what the code shows:

1. **`$D800-$D835` is not a 54-byte "bank 8 print settings" structure.** Only `$D801-$D814` belong to the print flow; `$D800`, `$D815`, `$D816` are unrelated; `$D818-$D88F` is the working set of the bank-7 shooter (mode `$07`), `$D890-$D9D6` the sound editor.
2. **`$D801/$D802`**: the nibble-packed margin is confirmed (`0:3339-3369`, hi = lines before, lo = lines after, default `$10,$03`), but `$D801` is a *custom-margin flag* and the value shown to the user is **`$D807`, 0..9 lines (default 3, set at `00:2F1B`)**, not a "FEED margin 0-30". `$D802` is recomputed for every photo (`8:4B32`).
3. **`$D803`** is the photo-slot loop index (0..`$3B`) of mode `$1E` and a pass counter in mode `$1C`; it is **not** the selector of the two layout templates (`8:50F6` vs `8:540D`); that choice is `$DBCB` (`8:4602`, `8:4656`).
4. **`$D804`** is **not** a copy count; it is the "first photo of the job" flag that selects the top margin `$10`.
5. **`$D806` bit 0** is not a "wide margin for wild frames": it is an option toggled with Start on the mode-`$1C` option screen (`8:42BC-42C1`) that adds a second print job (`8:46A3`) and sets `D801=1, D802=$10` for the first pass.
6. **`$D810`** is not a "wild-frame selector with x4 stride": it is the album-slot cursor (0..29) of the multi-photo print page; the `x4` (`8:4996`) is the cursor sprite x step. The 8 bytes `$D808-$D80F` are a selection bitmap.
7. **`$D814`** does not mean "printing in progress": it is set to 1 by the print engine on error or cancel (`0:3440`, `0:344E`) and cleared at job start; the loops stop when it is non-zero.
8. **`$D8C6`** (previous README: "written by a jump-table dispatcher at `5:5A57`"): row counter of the score printout (`5:5959`), with band flags in `$D8C7` (margin `$30` / `$03`). It is part of the sound editor.
9. **`$D8C8-$D8CA`, `$D8F3-$D8F5`, `$D8FA-$D8FC`**: field cursors (current field / previous field / return field) of the SOUND I, SOUND II and NOISE pages, not stamp-grid cursors.
10. **`$D8D9` bit 0 / bit 1 (Hello Kitty SRAM wipe)**: in the JP ROM `$D8D9` is byte 8 of the wave staging buffer `$D8D1-$D8F0` (written by `0:13C9`, `5:6AD1`); **no instruction in any bank references `$D8D9`** (the only literal hits are data bytes in graphics banks `$23/$25/$26`), and bank 1 `$4907-$49BC` is a data table in this ROM, not code. The Hello Kitty whole-SRAM initialiser has no counterpart here.
11. **`$D92E`** (written 81 times): request byte for a UI sound effect on hardware channel 1 (1 = cursor, 4/5 = select, 8 = value change). Its only reader (`0:10AC`) is never called from anywhere, so the effect is dead in this ROM.
12. **`$D9AD`** does feed SRAM `$10A1` bits 6-4 (`2:4ACE`): it is the **NOISE envelope period**, edited by field 2 of the NOISE page (`5:7149`, `5:719D`).
13. **`$D9D1-$D9F1` are not per-slot validity flags**: `$D9D1` tempo (15..240, default `$78`; SRAM `$10B9`), `$D9D2` saved-tune flag (`$10BA`), `$D9D3/$D9D5/$D9D6` start-menu selections, `$D9D7-$D9F7` = mode `$20` (a game), `$D9F8-$D9F9` = mode `$21` character pick.
14. **No 217-byte WRAM copy of the settings block exists in this region** (`$D93D-$D9D2` holds the unpacked sound part, 90 SRAM bytes -> 150 WRAM bytes, section 3.1); the 217 bytes are 215 data + 2 checksum bytes (`2:4BB2-4BF1`, checksum `2:432F` over `$D7` bytes).
15. **Mode table**: the previous trace stopped at mode `$1D`; modes `$1E-$21` exist (`8:4887`, `5:4000`, `5:74CC`, `9:5FE3`). Already fixed in the regenerated tables.

### Still inconclusive

* **`$D861`** (`7:5A22`, `5B73`, `5D5C`, `5F46`, `6114`): written at every wave init with 3, 2, 2, 3, 1 and never read in proven code (`?`).
* **`$D806` bit 0, second print job** (`8:46A3-4777`): it draws a page from banks `$1B/$09` (nine bank-9 layout routines `9:45B0 ... 9:4706`) and prints it with margin `$13`; what that page shows (photo info card? sticker sheet?) was not decoded.
* **`$D800`**: launched-from-extras flag; the exact on-screen option that sets it (`6:487A` option 2) and the screens it changes were not identified by label (`I`).
* **`$D816:$D817`**: sweep counter in bank 3 (`3:787A`), caller mode not identified (address-only attribution, `I`); no reset found.
* **`$D805`**: the load routine `0:2656` and the `2:517B` slot-pointer call were not read in depth; behaviour described from the callers.
* **Mode `$07` (`$D818-$D88F`)**: wave scripts of waves 1-4 (`7:5B38-6203`) were read only for the shared data layout, not wave by wave; the `+$40` shift of the third menu target when the best score `DAA3:DAA1` is below `$0020` (`7:59F9-5A0E`) is described as a probable unlock (`I`). `D818` (rapid fire) is unreachable in proven code; a bank-7 data-driven callback (`$792C/$7BF3/$7C62/$7CD1`) is the only way it could be set.
* **Mode `$20` (`$D9D7-$D9F9`)**: rules and graphics were read from the code, not played; the "three-ball juggling" reading and the game's name are inferences (`I`). `D9EB` is written but never read. The preview animation tables `5:7687`, `5:76D4`, `5:7713` were not matched to the tile graphics.
* **Mode `$0E` animators (`$D9FA-$D9FF`, `$DA00-$DA01`)**: the frame table `7:4354` is decoded (sprite pairs, durations, loop jumps) but not matched to the pictures; `DA00/DA01` belong to the next region.
* **Hi-score block `$DA96-$DAAB`** (outside this page): shown here only because `2:4BB2` saves it into SRAM `$10BB-$10D0`; its first 10 bytes (`$DA96-$DA9F`) were not examined.
* **Sound editor leftovers**: the roles tagged `I` in section 3 (performer animation bytes `$D892-$D89E`, `D91B-D91D`) are inferred from data flow; the performer sprite sheet is shared with mode `$20` (`5:7ABC` and `5:4F15` both add `00/48/90` to `$FFBA`).
