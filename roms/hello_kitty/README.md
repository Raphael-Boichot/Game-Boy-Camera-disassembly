# Pocket Camera (Hello Kitty)

MD5 `0a323bddc4f0159cea76cf44ed0c1a3c`. A late leaked prototype.

![What each byte of the Hello Kitty ROM is](kitty_rom_layout_map.png)

The map above is drawn by `tools/status_maps.py` (grey-blue = not analysed yet; it fills in as names, types and a trace are added here; per-bank counts in `assets/layout_by_bank_kitty.csv`).

Notes made before the work started (2026-11-01):

* **A different program, not a port.** Bank 0 shares only 2,698 of its 16,384 bytes with the Japanese ROM: it switches banks through `$2100` with the current bank in `$FF8B` (Japanese: `$2000`, `hRomBank`), and its far-call and table helpers are its own (`RST $18` is a jump-table dispatcher; far-call helpers near `00:0151-0194`). No bank is identical to a Japanese bank, and the internal title is `POCKETCAMERA_SN`. `tools/port_build.py` stops at the tracer here (the Japanese bank-0 entry points do not map); this ROM needs its own trace configuration, like a new ROM ([`HOWTO_NEW_ROM.md`](../../HOWTO_NEW_ROM.md)).
* **The save** (owner's [Inject-pictures repository](https://github.com/Raphael-Boichot/Inject-pictures-in-your-Game-Boy-Camera-saves#2021-07-01-update-structure-of-the-hello-kitty-pocket-camera-save), checked against a clean save that BGB made: Kitty ROM booted on an all-$00 SRAM for 1,200 frames): `$1000-$1009` the counters (taken, erased, transferred, printed, received), `$100A-$100C` the **Kitt** counter (3 x 2 BCD digits, low byte first), `$100D` = `$60` after formatting, `$1012-$1016` "Magic" followed by `$00` (no checksum: the game formats the block without one), `$11B2-$11D6` the photo vector state as in the other ROMs (with its echo after it). A clean save has no CoroCoro tag at `$1FFD-$1FFF`.
* **Unlocks.** The Kitts unlock the Strawberry Channel animations (TCRF: animation 1 and the credits are open, the others at Kitt milestones), and pay for the scratch cards (10) and the sliding puzzles (25). Emulator runs of this ROM must start from a save with the Kitt counter raised (`99 99 99`, 999,999 Kitts; made from the clean save, kept outside the repository), and the milestones are to be read in the code.

## L0: intake (2026-11-07)

Made by `tools/rom_intake.py` (command in its header); all numbers are byte counts read from [`intake/intake_header.csv`](intake/intake_header.csv) and [`intake/intake_banks.csv`](intake/intake_banks.csv).

* **Header (C).** 1,048,576 bytes = 64 banks; entry `00 C3 6A 17` (`nop; jp $176A`); title `POCKETCAMERA_SN`; cartridge type `$FC` (Pocket Camera mapper), 128 KiB SRAM, SGB flag `$03`, no CGB flag, destination Japan, licensee `33` / `01`, version `$00`; logo, header checksum and global checksum all valid.
* **Round trip (C).** mgbdis with no symbol file and rgbasm 1.0.4 rebuild the ROM byte-exact (L0).
* **Shared content with the sibling ROMs (C for the counts, I for what they mean).** A byte counts as shared when a 16-byte window holding it (not one repeated byte) occurs anywhere in the sibling ROM, at any address. Out of 1,048,576 bytes (226,227 of them padding runs of 16+ `$00` / `$FF`): 262,118 shared with the Japanese Rev A ROM, 263,035 with the international ROM, 263,164 with Gold, 119,140 with the early prototype. 217,204 bytes are shared with the Japanese ROM and not with the prototype, 12,264 the reverse: the Kitty build is much closer to the retail line than to `DEBAGAME`, which fits the owner's hypothesis of a build made from the Japanese version (I, to be tested on the code at L2-L3).
* **Where the Japanese ROM is closest.** Kitty banks `$09` / `$0A` (14,600 / 15,059 shared bytes, the best single Japanese bank being `$30`), `$12` (14,549, best Japanese bank `$2A`), `$11` (11,171, `$2A`), `$1C` (9,426, `$2E`), `$0E` (7,249, `$2F`) and `$04` (5,503, best Japanese bank `$0A`, the Japanese sensor bank). Bank 0 shares 4,155 bytes with the Japanese bank 0 (the README note above: a different bank-0 program).
* **Open (?).** In banks `$1E-$3D` the Kitty ROM shares more with the international ROM than with the Japanese one (60,423 bytes shared with the international ROM and not the Japanese one, mostly there; 65,363 the reverse, mostly in banks `$09-$12` and `$1C`). The owner's view (2026-11-07): the Kitty build is its own port, with its own assets, music and menus; only the sensor, printer and SRAM organisation are expected to be close to the Japanese ROM. Whether these shared windows are whole assets or small common pieces (blank or plain tiles, glyphs, fills) is checked asset by asset at L3; shared bytes are not used as evidence that an asset is shared.

## L1: every byte typed (2026-11-07)

The Kitty engine is not the Japanese one, so this ROM has its own tracer, `tools/kitty_trace.py` (its docstring lists the engine conventions read in the listing: ROM bank register `$2100` with shadow `hFF8B`, SRAM bank register `$4000` with shadow `hFF8C`, far call `$015B` / `$0165` with B = bank and HL = target and the callee returning through `jp $0173`, one-way far jump `$0155`, jump tables `$0189` / `$0194` / `rst $18`, far jump table `$01A0`, routines that take inline arguments after the call, the two LCDC-callback setters, the far callback given to `$1AB7`, the object creation `$205D`). Pipeline (SETUP.md, Hello Kitty): `kitty_trace.py` -> `trace/trace_kitty.json` and `trace/trace_kitty_unresolved.md`; `tools/kitty_types.py` -> `disasm/sym_types_kitty.csv`, `assets/copy_sites_kitty.csv`, `trace/rom_map_kitty.csv`, `disasm/sym_names_kitty.csv`; `tools/sym_build.py` -> `pocketcamera_kitty.sym`. All seven files are generated from the ROM, the hand file `trace/extra_roots_kitty.json` and the run files `port/cov_kitty_*.npz` (L2).

* **Code (C).** 61,153 bytes of proven code: recursive descent from the entry, the five interrupt vectors, the rst and bank-0 helpers, 667 far calls resolved from constants on the straight line before the call, the 124 object descriptors of bank 2 created with a constant address, and 258 entries observed in the runs (L2). The main loop (`00:0CF2`) calls the mode routine through the far jump table `ModeTable` (`00:0D00`, 31 `{lo, hi, bank}` entries, mode in `hFF8D`); each mode dispatches its state (`hFF8E`) through a word table read by `$0189`. Mode and state are set by `$01B2` (mode = A), `$01BD` (state = A), `$01C8` (B, C) and `$01D1` (two inline bytes).
* **Table lengths (I where cut by hand).** A word table is read up to the lowest target seen; 9 tables are cut by hand and 8 indexed `jp hl` tables are read by hand in `trace/extra_roots_kitty.json`, each with its reason (a word that lands inside an instruction or inside argument bytes, a next table that starts there, a mode whose code sets no higher state; the sound driver's id bounds `cp $0B` / `cp $3F` / `cp $13` give 10 / 62 / 18 entries, the counts of the Japanese driver). The trace also reports, per state table, the states that the code sets for that mode (`state_check` in the trace file).
* **Data typed by a reason (C).** 833,541 bytes of data typed by a reason: the jump tables (width 2 or 3), the inline argument bytes after the calls, the sources of 235 of the 333 traced copy-routine calls whose bank, source and length are constants (`assets/copy_sites_kitty.csv`: tiles `data,16`, tile maps `data,32` / `data,20`, WRAM / OAM data), and the bytes the core runs read as data (one block per run of read bytes, the reader routines in the note). Each block start carries a label named by kind and address only (`Gfx_BB_AAAA`, `Map_BB_AAAA`, `Data_BB_AAAA`, `JumpTable_BB_AAAA`, `FarJumpTable_BB_AAAA`, `ModeTable`).
* **The rest.** 74,186 bytes of padding (runs of 16+ `$00` that no run read; 292 fewer since 2026-11-12, where a data or leftover label of L3 falls inside a run); 79,696 bytes of data on the default typing (`.data`, 16 per row): bytes no traced copy names and no run read.

## L2: code proven and observed (2026-11-07)

* **0 indirect sites left unresolved (C).** The dynamic ones are read by hand in `trace/extra_roots_kitty.json` with their reason: the two object engines (per-frame routine and script command calls at `00:2113` / `00:212F` and `01:59E7` / `01:59FE`; objects are 23-byte slots at `$DAEE`, created by `$205D` from a descriptor in bank 2), the script command that calls the word after it (`02:6601` / `02:6612`), and object creations whose descriptor is returned by a far call; their targets come from the runs (observed roots).
* **Observed (C).** 47,717 of the 61,153 bytes of proven code ran: in the project's core (`tools/kitty_coverage.py`, novelty search over joypad input, four runs of 25 minutes, one with the core's printer model on the link port, one from the owner's unlocking save, plus `tools/kitty_scenarios.py` for the boot conditions), and in BGB for the photo exchange between two linked units (`tools/kitty_bgb_link.py`; logging breakpoints on the 389 blocks no core run had executed, 16 hit; `tools/kitty_bgb_hits.py` credits a block when its first instruction ran). The receiving unit's SRAM changes in the first photo slot (C, BGB state).
* **Boot conditions (C, core and BGB).** The keys read at power-on are kept in `$D8D8`: every key but B held gives `$FD` and mode `$0D` state 0, the **quick factory check** (`CHECK`, `PLEASE WAIT`, then `GAIN8` / `GAINA` and `NG` with BGB's fake sensor); a blank SRAM of `$AA` gives `$FF` and mode `$0D` state 3, the **factory calibration** (`STORE`, `PLEASE WAIT`, `END`). The same two entries as the Japanese ROM (§18), with the same key combination.
* **Not run yet.** 13,006 bytes of proven code never ran in any run (what they are: below, "The never-run code"); 4 modes (`$13`, `$15`, `$16`, `$1D`) draw no screen even when forced (the mode table patched in a copy of the ROM, evidence I), and 11 more show a screen only when forced (below). No code stores a constant mode `$13` or `$15`-`$1D` anywhere in the ROM (raw byte search of `ld b / ld a` + the mode setters); `$02:7EA2` sets the mode from an object's fields, so these may be reached through an object script.

* **Printing (C, BGB).** With the project's printer helper on the link (`tools/kitty_bgb_print.py`), START on the photo-taken screen prints: mode `$06` shows a little car and "please wait" (state `$1F`, A spin / B cancel), the car drives off (state `$21`), and A starts a game while the printer works (state `$24`: Hello Kitty jumps to catch falling fruits, the Kitts won and the record at the top right, a row of flowers at the top left). Kept busy by the helper (`PRN_POLLS=1000000`: every inquiry after the PRINT answers busy), the game runs on for 6,000 frames; the helper received one page. The apples caught are counted in `$D94F` (`PrintGame_DrawAppleCount`, state `$23`) and added to the Kitts when the game ends.
* **Printing from the album: the print frames (C, BGB, 2026-11-08).** The third icon of the album binder (mode `$03` state `$02`) opens mode `$06` state `$03`: the photo in one of **six print frames**, chosen with Left / Right (flowers and apples, HELLO KITTY, a plain bevel, a "きょうのいちばん" (today's best) banner, an empty banner, Kitty heads); state `$0A` then offers START (the photo, then a second page with the album comment lines, the ID card fields and Kitty: states `$15` and `$1C`, `Print_SetFrameSide`, `Print_LoadFrameGfx`), A (the photo only) or B. The helper received each frame as printed ([`screens/print_frames.png`](screens/print_frames.png): the screen above, the printed photo page below; the photo is the core's stand-in sensor picture).
* **Printer errors (C, BGB, 2026-11-08).** `PRN_ERR` of the printer helper (§16.16) replaces printer replies: no answer to INIT or `$FF` gives **print error #02** ("is the Pocket Printer connected?"), as does bit 4 (packet error) on one inquiry while printing; held for 200 inquiries while printing, bit 5 (paper jam) gives **#03** ("is the print sticker jammed?"), bit 6 gives **#04**, bit 7 (low battery) gives **#01** (mode `$14` state `$01`, [`screens/print_errors.png`](screens/print_errors.png)); bits 0 to 3 are ignored and the print completes.
* **Print intensity and the album page (C, BGB, 2026-11-12, owner's hint).** On the print frame screen (mode `$06` state `$03`), START held shows the print intensity (state `$0F`, `Mode06_State0F`: うすい light at the top, こい dark at the bottom, a squirrel on the scale that Up / Down move); Up / Down instead fade to state `$02` and then `$04`, the **wild frames** (taller frames printed around the photo: the Hello Kitty pattern, the house, the stickers, Kitty's Family, MEMO, HELLO KITTY; Up / Down change the frame, Left / Right return to the normal frames, A shows the photo in it, state `$06`, then prints it).
* **Printing with no printer: four error pictures at random (C, BGB, 2026-11-12, owner's hint).** START or A in the print menu with nothing on the link gives print error #02, its message sliding from right to left under a picture that `Mode14_State00` draws at random: `Rng_Next & 3` picks one of the four 3-byte records of `06:4464` (`3E:5C00` Badtz-Maru alone, `3E:6A00` three characters, one reading a book, `3F:4000` two characters in hoods, `3D:6A00` three characters and a top hat), $800 bytes copied to `$9000` and $600 to `$8000`; twelve BGB runs with different timings showed all four (the screen tree shows them in the print error panel).
* **The おもしろレンズ slide show (C, BGB, 2026-11-12, owner's key path).** In the live view (mode `$02` state `$01`), Down, Down open おもしろレンズ Ⓐ (the lens chooser, Hello Kitty saying HI! next to a "?" lens); A on the "?" lens starts a slide show of Hello Kitty pictures inside the camera frame (Kitty with her teddy bear, Kitty on lined paper, Kitty with a lion, a bear face, Kitty with a speech balloon, blank pages between them), every few seconds a new picture; the game stays in mode `$02` state `$01`. The 96 picture effects of `04:5E8A`, forced one by one in BGB (each in a patched copy), are transforms of the live picture only: the slide show is not one of them.
* **Stamps (C, BGB, 2026-11-12, owner).** The second icon of the album binder (mode `$03` state `$02`, Down A) opens the stamp screen over the photo (mode `$05` state `$06`, until now seen only with a patched mode table); START opens the stamp window: 8 pages, chosen with Right Right (the tab column) and Up / Down: large Kitty stamps (30), small Kitty and friends stamps, face parts, kana in three sizes, kanji, shapes and arrows. Every row of every page, as the window shows it while scrolling: [`screens/stamps_kitty.png`](screens/stamps_kitty.png).
* **Lenses (C, BGB, 2026-11-13, owner).** In the live view, Up / Down step through 20 lenses: ふつうのレンズ (normal), Up: おばけレンズ ①-⑧ ("ghost" lenses: mirrors, flips, stretches, a 2 x 2 split), Down: おもしろレンズ Ⓐ-Ⓚ ("fun" lenses: Ⓐ the slide show above, the others Hello Kitty pictures beside, above or between 2, 2 x 2 photo windows); every lens, and the live view after A on each fun lens: [`screens/lenses_kitty.png`](screens/lenses_kitty.png).
* **The no-photo picture (I, BGB, 2026-11-13).** `Photo_LoadEmptyPicture` draws `11:7000` (しゃしんがないよ, "no photo") when `Photo_FindSlotA` finds no slot for a photo number (album photo view, stamp screen, exchange receiver, slide show). Normal play keeps the numbers compact (deleting photo 01 of two renumbers the other) and no key path was found; a copy with `Photo_FindSlotA` patched to fail shows it in the album photo view (`screens/extra_03_05_noslot.png`, dashed in the tree).
* **The owner's paths in the core (2026-11-13).** `tools/kitty_core_paths.py` replays the paths above in the core so that the maps count them (`trace/cov_kitty_paths.npz`): the six wild frames printed, the print intensity (START held, Up / Down), printing with nothing on the link (from the photo-taken screen and from the album), the 20 lenses and the slide show, the 8 stamp pages; with them the never-run proven code goes from 7,607 to 7,324 bytes not run by anything.

When the giver has no photo, both show "no photo to give / receive" after a time-out. `Link_SumSlotBuffer` (unused in the Japanese ROM) runs here.
* **Super Game Boy (C, BGB, 2026-11-08).** BGB as a Super Game Boy (`SystemMode=2`, `tcrf_check/tools/bgb_sgb_capture.sh`) shows a pink houndstooth border with the "Hello Kitty" logo and four coloured Kitty faces in the corners ([`screens/sgb_border.png`](screens/sgb_border.png), the title screen, 256 x 224); read watchpoints on the five transfer sources of bank `$08` (`08:40D0`, `4146`, `41F6`, `5206`, `6216`) all hit, so the never-read data of bank `$08` is the SGB data.

* **What the flowers count, and why they grow at every visit (C, code and BGB).** Each vine is a script of the slot engine at `$DC67` (6 slots of 20 bytes, `01:597E` ScriptSlots_Add, run by `01:59C6`). State 0 of mode `$0C` empties the slots (`01:596C`) and starts five vines, one per counter, whose first step reads the counter from WRAM `$DAC9` (the copy of SRAM `$1000-$1011`) into hFFEA-EB: taken x1 (`01:571C`), thrown away x1 (`01:5736`), exchanged x11 (`01:5750`), received boys + girls x11 (`01:577D`), printed x6 (`01:57C5`). The shared script `01:56C7` then grows three kinds of flower one by one: one per hundred (0-19, 20 from 2,000 on), one per ten, one per unit, so 12 photos give 3 flowers and one exchange gives 2 (11). BGB pictures with one exchange, one print, one boy and one girl received show 2, 6, 2 and 2 flowers; with 9,999 taken the row is full, but with exactly 100 taken BGB showed no flower 600 frames after opening (?, not explained yet). Nothing of a previous visit is kept: a BGB run with read and write watchpoints over two visits in a row (SRAM `$A000-$BFFF`, `$D800-$D8FF`, the counters `$DAC9-$DAD6`, the slots `$DC67-$DCDE`) shows no SRAM access in mode `$0C`, the counters read only by the digit drawing (`06:581C`, `06:58D4`) and the five vine routines, and the slots emptied again at each entry; the flowers grow again on the second visit with no count changed. The animation is therefore a replay of the current counts, not a comparison with the last visit.

## L3: names (done, 2026-11-12)

* **Data names (L3, 2026-11-12).** The 822 placeholder labels of L1 (`Data_BB_AAAA` 720, `Gfx_` 41, `Map_` 45, `JumpTable_` 16) are gone. `tools/kitty_data_names.py` (layer 5 of `tools/kitty_names.py`) works in the Japanese convention: 241 of them sat on the inline arguments of a call (`Copy_FarInline`, `Lcd_SetupInline` ...) and are dropped, the bytes belong to the call as in the Japanese listing; inside the others, every stretch of 32 bytes or more (padding runs aside) that no run reads or executes, no code names and no loader table explains is cut out as `Leftover_BB_AAAA` (110, tag I, final, `disasm/sym_settled_unused_kitty.csv`), and 10 more such stretches are entries of a table of their bank that no run reached (`Snd_0F_57AE_EntryOf572F`, the songs of the song table never played; `KeyPrompt_LoadSounds_Tbl5F7F_Entry5E8E` ...; tag I, doubts list); a block whose bytes hold two kinds is cut where the kind changes (38 cuts). Each block is then named by its kind, from the evidence of `tools/kitty_layout_kinds.py` (display tracker, loader tables, constant copies, readers) or its reader, and by its consumer: `Gfx_BB_AAAA_<context>`, `Map_`, `Frame_` (print and camera frames), `Snd_`, `OamList_` (sprite layouts), `ObjScript_` (object engine records), `Script_` (script slots), `Pal_..._Palettes`, `Src_` (copied, the destination never seen: kind not settled), `<Routine>_TblAAAA` and `<Routine>_JumpTblAAAA` for the tables of one routine, and the Japanese name (its address part made the Kitty one) for 18 blocks that are unique exact copies of named Japanese blocks (the sound-effect data `Sfx1_*`, `Snd_FreqTbl`, `Rng_InitOrder`, the Super Game Boy packets `Sgb_MltReqPackets` ...). The context is the routine whose code names the address, else the screen the bytes are first read on (`ModeMM_<Mode>_StateSS`, after the fade of mode `$1E`: [`trace/read_screens_kitty.npz`](trace/read_screens_kitty.npz), two 40-minute core runs of `tools/kitty_read_screens.py`; 575 names), else the routine that reads them. Tags: C when an organic run reads the bytes (608), I when only forced runs do or nothing reads them (15).
