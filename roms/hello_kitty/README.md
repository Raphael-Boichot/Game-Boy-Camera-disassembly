# Pocket Camera (Hello Kitty)

MD5 `0a323bddc4f0159cea76cf44ed0c1a3c`. A late leaked prototype.

![What each byte of the Hello Kitty ROM is](kitty_rom_layout_map.png)

The map above is drawn by `tools/status_maps.py` (grey-blue = not analysed yet; it fills in as names, types and a trace are added here; per-bank counts in `assets/layout_by_bank_kitty.csv`).

Notes made before the work started (2026-11-01):

* **A different program, not a port.** Bank 0 shares only 2,698 of its 16,384 bytes with the Japanese ROM: it switches banks through `$2100` with the current bank in `$FF8B` (Japanese: `$2000`, `hRomBank`), and its far-call and table helpers are its own (`RST $18` is a jump-table dispatcher; far-call helpers near `00:0151-0194`). No bank is identical to a Japanese bank, and the internal title is `POCKETCAMERA_SN`. `tools/port_build.py` stops at the tracer here (the Japanese bank-0 entry points do not map); this ROM needs its own trace configuration, like a new ROM ([`HOWTO_NEW_ROM.md`](../../HOWTO_NEW_ROM.md)).
* **The save** (owner's [Inject-pictures repository](https://github.com/Raphael-Boichot/Inject-pictures-in-your-Game-Boy-Camera-saves#2021-07-01-update-structure-of-the-hello-kitty-pocket-camera-save), checked against a clean save that BGB made: Kitty ROM booted on an all-$00 SRAM for 1,200 frames): `$1000-$1009` the counters (taken, erased, transferred, printed, received), `$100A-$100C` the **Kitt** counter (3 x 2 BCD digits, low byte first), `$100D` = `$60` after formatting, `$1012-$1016` "Magic" followed by `$00` (no checksum: the game formats the block without one), `$11B2-$11D6` the photo vector state as in the other ROMs (with its echo after it). A clean save has no CoroCoro tag at `$1FFD-$1FFF`.
* **Unlocks.** The Kitts unlock the Strawberry Channel animations (TCRF: animation 1 and the credits are open, the others at Kitt milestones), and pay for the scratch cards (10) and the sliding puzzles (25). Emulator runs of this ROM must start from a save with the Kitt counter raised (`99 99 99`, 999,999 Kitts; made from the clean save, kept outside the repository), and the milestones are to be read in the code.

## L0: intake (2026-11-07)

Made by `tools/rom_intake.py` (command in its header); all numbers are byte counts read from [`intake/intake_header.csv`](intake/intake_header.csv) and [`intake/intake_banks.csv`](intake/intake_banks.csv).

* **Header (C).** 1,048,576 bytes = 64 banks; entry `00 C3 6A 17` (`nop; jp $176A`); title `POCKETCAMERA_SN`; cartridge type `$FC` (Pocket Camera mapper), 128 KiB SRAM, SGB flag `$03`, no CGB flag, destination Japan, licensee `33` / `01`, version `$00`; logo, header checksum and global checksum all valid.
* **Round trip (C).** mgbdis with no symbol file and rgbasm 1.0.4 rebuild the ROM byte-exact (L0).
* **Shared content with the sibling ROMs (C for the counts, I for what they mean).** A byte counts as shared when a 16-byte window holding it (not one repeated byte) occurs anywhere in the sibling ROM, at any address. Out of 1,048,576 bytes (226,227 of them padding runs of 16+ `$00` / `$FF`): 262,118 shared with the Japanese Rev A ROM, 263,035 with the international ROM, 263,164 with Gold, 119,140 with the early prototype. 217,204 bytes are shared with the Japanese ROM and not with the prototype, 12,264 the reverse: the Kitty build is much closer to the retail line than to `DEBAGAME`, which fits the owner's hypothesis of a build made from the Japanese version (I, to be tested on the code at L2-L3).
* **Where the Japanese ROM is closest.** Kitty banks `$09` / `$0A` (14,600 / 15,059 shared bytes, the best single Japanese bank being `$30`), `$12` (14,549, best Japanese bank `$2A`), `$11` (11,171, `$2A`), `$1C` (9,426, `$2E`), `$0E` (7,249, `$2F`) and `$04` (5,503, best Japanese bank `$0A`, the Japanese sensor bank). Bank 0 shares 4,155 bytes with the Japanese bank 0 (the README note above: a different bank-0 program).
* **Open (?).** In banks `$1E-$3D` the Kitty ROM shares more with the international ROM than with the Japanese one (60,423 bytes shared with the international ROM and not the Japanese one, mostly there; 65,363 the reverse, mostly in banks `$09-$12` and `$1C`). The owner's view (2026-11-07): the Kitty build is its own port, with its own assets, music and menus; only the sensor, printer and SRAM organisation are expected to be close to the Japanese ROM. Whether these shared windows are whole assets or small common pieces (blank or plain tiles, glyphs, fills) is checked asset by asset at L3; shared bytes are not used as evidence that an asset is shared.

## L1: every byte typed (2026-11-07)

The Kitty engine is not the Japanese one, so this ROM has its own tracer, `tools/kitty_trace.py` (its docstring lists the engine conventions read in the listing: ROM bank register `$2100` with shadow `hFF8B`, SRAM bank register `$4000` with shadow `hFF8C`, far call `$015B` / `$0165` with B = bank and HL = target and the callee returning through `jp $0173`, one-way far jump `$0155`, jump tables `$0189` / `$0194` / `rst $18`, far jump table `$01A0`, routines that take inline arguments after the call, the two LCDC-callback setters, the far callback given to `$1AB7`, the object creation `$205D`). Pipeline (SETUP.md, Hello Kitty): `kitty_trace.py` -> `port/trace_kitty.json` and `port/trace_kitty_unresolved.md`; `tools/kitty_types.py` -> `disasm/sym_types_kitty.csv`, `assets/copy_sites_kitty.csv`, `port/rom_map_kitty.csv`, `disasm/sym_names_kitty.csv`; `tools/sym_build.py` -> `pocketcamera_kitty.sym`. All seven files are generated from the ROM, the hand file `disasm/extra_roots_kitty.json` and the run files `port/cov_kitty_*.npz` (L2).

* **Code (C).** 60,622 bytes of proven code: recursive descent from the entry, the five interrupt vectors, the rst and bank-0 helpers, 667 far calls resolved from constants on the straight line before the call, the 124 object descriptors of bank 2 created with a constant address, and 258 entries observed in the runs (L2). The main loop (`00:0CF2`) calls the mode routine through the far jump table `ModeTable` (`00:0D00`, 31 `{lo, hi, bank}` entries, mode in `hFF8D`); each mode dispatches its state (`hFF8E`) through a word table read by `$0189`. Mode and state are set by `$01B2` (mode = A), `$01BD` (state = A), `$01C8` (B, C) and `$01D1` (two inline bytes).
* **Table lengths (I where cut by hand).** A word table is read up to the lowest target seen; 9 tables are cut by hand and 8 indexed `jp hl` tables are read by hand in `disasm/extra_roots_kitty.json`, each with its reason (a word that lands inside an instruction or inside argument bytes, a next table that starts there, a mode whose code sets no higher state; the sound driver's id bounds `cp $0B` / `cp $3F` / `cp $13` give 10 / 62 / 18 entries, the counts of the Japanese driver). The trace also reports, per state table, the states that the code sets for that mode (`state_check` in the trace file).
* **Data typed by a reason (C).** 804,917 bytes of data typed by a reason: the jump tables (width 2 or 3), the inline argument bytes after the calls, the sources of 235 of the 333 traced copy-routine calls whose bank, source and length are constants (`assets/copy_sites_kitty.csv`: tiles `data,16`, tile maps `data,32` / `data,20`, WRAM / OAM data), and the bytes the core runs read as data (one block per run of read bytes, the reader routines in the note). Each block start carries a label named by kind and address only (`Gfx_BB_AAAA`, `Map_BB_AAAA`, `Data_BB_AAAA`, `JumpTable_BB_AAAA`, `FarJumpTable_BB_AAAA`, `ModeTable`).
* **The rest.** 86,911 bytes of padding (runs of 16+ `$00` that no run read); 96,126 bytes of data on the default typing (`.data`, 16 per row): bytes no traced copy names and no run read.

## L2: code proven and observed (2026-11-07)

* **0 indirect sites left unresolved (C).** The dynamic ones are read by hand in `disasm/extra_roots_kitty.json` with their reason: the two object engines (per-frame routine and script command calls at `00:2113` / `00:212F` and `01:59E7` / `01:59FE`; objects are 23-byte slots at `$DAEE`, created by `$205D` from a descriptor in bank 2), the script command that calls the word after it (`02:6601` / `02:6612`), and object creations whose descriptor is returned by a far call; their targets come from the runs (observed roots).
* **Observed (C).** 45,438 of the 60,622 bytes of proven code ran: in the project's core (`tools/kitty_coverage.py`, novelty search over joypad input, four runs of 25 minutes, one with the core's printer model on the link port, one from the owner's unlocking save, plus `tools/kitty_scenarios.py` for the boot conditions), and in BGB for the photo exchange between two linked units (`tools/kitty_bgb_link.py`; logging breakpoints on the 389 blocks no core run had executed, 16 hit; `tools/kitty_bgb_hits.py` credits a block when its first instruction ran). The receiving unit's SRAM changes in the first photo slot (C, BGB state).
* **Boot conditions (C, core and BGB).** The keys read at power-on are kept in `$D8D8`: every key but B held gives `$FD` and mode `$0D` state 0, the **quick factory check** (`CHECK`, `PLEASE WAIT`, then `GAIN8` / `GAINA` and `NG` with BGB's fake sensor); a blank SRAM of `$AA` gives `$FF` and mode `$0D` state 3, the **factory calibration** (`STORE`, `PLEASE WAIT`, `END`). The same two entries as the Japanese ROM (§18), with the same key combination.
* **Not run yet.** 15,184 bytes of proven code never ran in any run; 4 modes (`$13`, `$15`, `$16`, `$1D`) draw no screen even when forced (the mode table patched in a copy of the ROM, evidence I), and 11 more show a screen only when forced (below). No code stores a constant mode `$13` or `$15`-`$1D` anywhere in the ROM (raw byte search of `ld b / ld a` + the mode setters); `$02:7EA2` sets the mode from an object's fields, so these may be reached through an object script.

* **Printing (C, BGB).** With the project's printer helper on the link (`tools/kitty_bgb_print.py`), START on the photo-taken screen prints: mode `$06` shows a little car and "please wait" (state `$1F`, A spin / B cancel), the car drives off (state `$21`), and A starts a game while the printer works (state `$24`: Hello Kitty jumps to catch falling fruits, the Kitts won and the record at the top right, a row of flowers at the top left). Kept busy by the helper (`PRN_POLLS=1000000`: every inquiry after the PRINT answers busy), the game runs on for 6,000 frames; the helper received one page.
* **Record book flowers (C, BGB).** Opened from a save whose counters were set by hand in the SRAM (taken 5 at `$1000`, erased 3 at `$1002`, printed 2 at `$1006`; Kitts 999,999), the record book (mode `$0C` state 1) grows a flower on the vine under each counter every few frames: [`screens/record_book_flowers.png`](screens/record_book_flowers.png), 20 frames apart.
* **What the flowers count, and why they grow at every visit (C, code and BGB).** Each vine is a script of the slot engine at `$DC67` (6 slots of 20 bytes, `01:597E` ScriptSlots_Add, run by `01:59C6`). State 0 of mode `$0C` empties the slots (`01:596C`) and starts five vines, one per counter, whose first step reads the counter from WRAM `$DAC9` (the copy of SRAM `$1000-$1011`) into hFFEA-EB: taken x1 (`01:571C`), thrown away x1 (`01:5736`), exchanged x11 (`01:5750`), received boys + girls x11 (`01:577D`), printed x6 (`01:57C5`). The shared script `01:56C7` then grows three kinds of flower one by one: one per hundred (0-19, 20 from 2,000 on), one per ten, one per unit, so 12 photos give 3 flowers and one exchange gives 2 (11). BGB pictures with one exchange, one print, one boy and one girl received show 2, 6, 2 and 2 flowers; with 9,999 taken the row is full, but with exactly 100 taken BGB showed no flower 600 frames after opening (?, not explained yet). Nothing of a previous visit is kept: a BGB run with read and write watchpoints over two visits in a row (SRAM `$A000-$BFFF`, `$D800-$D8FF`, the counters `$DAC9-$DAD6`, the slots `$DC67-$DCDE`) shows no SRAM access in mode `$0C`, the counters read only by the digit drawing (`06:581C`, `06:58D4`) and the five vine routines, and the slots emptied again at each entry; the flowers grow again on the second visit with no count changed. The animation is therefore a replay of the current counts, not a comparison with the last visit.
* **Scratch card (C, BGB).** Played with keys: the board (mode `$10` state 2), the six spots scratched (state 4: cherries worth 20 Kitts, bears worth 40 Kitts), and the host's question when B is pressed in the middle (mode `$0E` state `$20`: quit or continue).
* **Name card (C, BGB).** The owner ID card is reached with keys only: take three photos, open Name in the option menu, pick the three photos (mode `$0B` state 4), type a name (state 8), then the blood type (state `$0A`), the birthday (state `$0C`) and boy / girl (state `$0E`); END shows the finished card (mode `$0A` state 1: ID number, name, birthday; its three photos take turns) and its menu (state 2: change, print, cancel). No new code ran on this path: the core runs had already executed it.
* **Strawberry Channel (C, BGB).** Left alone, a channel plays its animation in a loop (channel 1: Hello Kitty driving a little car; 2,400 frames watched, screenshots every 60 frames). Left / Right change the channel (the dots at the bottom; from the unlocking save: car, slide, seesaw, tree, swing, a picnic titled おそとで あそぼ, and channel 7, the **credits**: a spiral, then the staff list rolls ("Hello Kitty Pocket Camera Staff", supervisor, director, programmers, designers, sound, special thanks, producer, "Presented by Nintendo") and starts again, [`screens/strawberry_channel_credits.png`](screens/strawberry_channel_credits.png); then back to channel 1, [`screens/strawberry_channel_pages.png`](screens/strawberry_channel_pages.png)); Up / Down change only the byte `$D8DC` (a bar with arrows shows at the top left when a channel starts: probably the volume, I). No new code ran.
* **What is still missing (C, the runs).** [`kitty_rom_reachability_map.png`](kitty_rom_reachability_map.png), drawn by `tools/kitty_reach_map.py` from the two run files, the trace classes and the type rows: 15,180 bytes of proven code never executed (red; most in banks `$04` (sensor), `$06`, `$00`, `$01`, `$07` and `$0F`), 76,853 bytes of data never read and explained by nothing (grey-blue; most in banks `$12`, `$08`, `$03`, `$11`), 38,300 bytes never read but explained by a loader site or a table (orange), 812,150 bytes executed or read (blue), the rest never-read padding and fill. No forced or proven-dead category yet (the forced screens were BGB pictures, not coverage runs).

## L3: names (in progress, 2026-11-08)

* **Names.** 1,399 names (C 1,310 / I 87 / ? 2), merged from five layers by `tools/kitty_names.py`: 807 block labels by kind and address (L1), 307 mode and state names (`ModeMM_<Name>` from the BGB screens, `ModeMM_StateTable`, `ModeMM_StateSS`; the names of `disasm/mode_names_kitty.csv`, tagged I for the 14 modes seen only forced), 201 names ported from the Japanese ROM, 35 names of edited Japanese routines, 49 hand names (the bank-0 engine and the record book, `disasm/sym_names_kitty_hand.csv`).
* **Same code as the Japanese ROM (C).** `tools/kitty_match_jp.py` searches every Japanese routine of 12+ bytes in the Kitty code with the build-dependent operands as wildcards (16-bit addresses, the HRAM byte of `ldh`): 230 of 1,891 are found, 204 at exactly one place. They are the **printer protocol** (`Prn_*`, bank 0), the **link cable** (`Link_*`, bank 0), the **sensor bank** (the Japanese bank `$0A` in Kitty bank `$04`: calibration copy and check, exposure bands, threshold convergence, dither ramps, the image effects `Fx*`), the **SRAM magic comparison** (`Sram_CompareMagic`, one Kitty routine for the three Japanese copies, tag ?), and **107 sound-effect routines** of the Japanese sound bank `$1F` in Kitty bank `$0F`. A port is tagged C from 16 bytes, I below.
* **Edited copies (I).** `tools/kitty_similar_jp.py` compares the instruction sequences of the routines not found exactly: 52 near matches (ratio >= 0.85), among them the **factory calibration** (`Cam_FactoryMeasure1` / `Cam_FactoryMeasure2`, ratio 0.998 / 0.997), the **quick factory check** (`Cam_CalibSanityCheck_Measure`, 0.993), `Cam_CommitVectorToSRAM`, `Sram_ComputeImageChecksums`, `Sgb_SendPacket`, `Img_ReduceToThumbnail` and the flipped image effects.
* **Owner's hypotheses so far.** Sensor, printer, link and SRAM code: the same routines as the Japanese ROM (C for the exact matches). Sound: the effect routines are shared; the music data is still to compare. Menus: no routine of the other Japanese banks matches (only banks `$00`, `$02`, `$07`, `$0A` and `$1F` have matches; the 31 Kitty modes have their own code).
* **Next.** About 890 routine entries (call, table and observed entries) have no name yet; they are named by reading, bank by bank, menus first; then the doubts list.
