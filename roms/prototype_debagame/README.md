# Pocket Camera Prototype (Japan)

MD5 `19b50a5f67ef4f0d015e7d813370756e` as dumped (`1d8097de3497db8b182bcd2a984b6063`: the header-patched copy for BGB, see "Two images" below). An early leaked development ROM. Its header title is blank, but its title screen reads デバガメテスター ("Debagame Tester"), SECOND IMPACT, Ver10.24, 1997 Nintendo R&D Dept. (C, BGB), and its menu offers SRAM, bank and protect tests, a movie test, a gallery and a link (COM) entry: a test program for the camera cartridge hardware rather than an early camera program (I, from its screens, L2 below). The development paths `C:\DEBAGAME\TOOL` and `C:\DEBAGAME\ISD` left in the ROM (file offsets `$6B382`, `$F50FF`, `$F6322`) carry the same name, and SECOND IMPACT matches the name of the dump, `GBD-IMPACT8M`. TCRF documents it, and the TCRF page shows two assembly listings of it with Japanese comments (https://tcrf.net/index.php?title=Proto:Game_Boy_Camera&oldid=1982808, section Source Code).

![What each byte of the early prototype ROM is](proto_rom_layout_map.png)

The map above is drawn by `tools/status_maps.py` (grey-blue = not analysed yet; it fills in as names, types and a trace are added here; per-bank counts in `assets/layout_by_bank_proto.csv`).

This folder will hold the symbol file and the tables of this ROM, built with the tools of the repository and the playbook [`HOWTO_NEW_ROM.md`](../../HOWTO_NEW_ROM.md). The ROM is not in the repository (supplied by the owner outside it).

* **Round trip (C).** The standard mgbdis Makefile ends with `rgbfix -v -p 255`, which rebuilds the image as dumped with four header bytes changed: the ROM-size byte `$0148` (`$03` -> `$05`, the size of the padded file) and the three checksum bytes (`$014D` `$4C` -> `$4A`, `$014E-$014F` `$0000` -> `$6145`). The header bytes are data in the listing, so linking without rgbfix gives the image as dumped byte for byte (`tools/rom_intake.py --no-rgbfix`). The BGB copy rebuilds byte-exact with the standard Makefile (rgbfix leaves its already correct header unchanged). Any later build of this ROM (L1 checks, an L5 tree) must skip rgbfix too.
* **Intake (C, `intake/intake_banks.csv`, `intake_header.csv`).** Command in `tools/rom_intake.py`; references: the Japanese, international, Gold and Hello Kitty ROMs. Of the 1,048,576 bytes, 348,519 are padding (runs of 16 or more equal `$00` / `$FF`); 177,724 are covered by a 16-byte window that also occurs somewhere in the Japanese ROM, 161,081 in the Hello Kitty ROM. Shared content is not shared code: much of the prototype is leftover text and copies of its own banks (the section on the source text above and the symbol tables below), and a 16-byte window can be a tile or a table.

## L1: the trace and the symbol file (2026-11-08)

Pipeline (seconds; SETUP.md, prototype): `tools/proto_symtab.py`, `tools/proto_trace.py` (with the hand file `trace/extra_roots_proto.json`), `tools/proto_types.py`, then `tools/sym_build.py`. Every generated file is rebuilt and compared by the checker (`--rom-proto`).

* **The running program is bank `$00` alone (C, static trace).** The trace from the entry and the four interrupt vectors proves 7,915 instructions, 12,893 bytes of proven code, all in bank `$00`, with 0 indirect sites left unresolved (`trace/trace_proto_unresolved.md`). No traced instruction calls or jumps into `$4000-$7FFF`: the other banks are only read as data. The eight hand entries (one jump table; the two bank writes of the ROM self-test; the call of the OAM DMA stub in HRAM; four call sites of two callees, `00:0780` and `00:32E3`, that select a bank without restoring it, which matters only for banked calls and there are none) are in `trace/extra_roots_proto.json`, each with its reason.
* **Engine (C, read in the listing; `tools/proto_trace.py` docstring).** No banked-call helper: every switch is written inline (`ldh a,[$FFFD]; push af`, `ld a,N; ldh [$FFFD],a; ld [$2100],a`, the work, then the saved bank back). `rst $00` / `rst $08` restart at `$0150`; `rst $28` is a jump table of words placed after the `rst` (not used by the traced code); `rst $38` is the fill byte. The main loop calls `00:01FE`, which dispatches on `GAME_SEQ` (`$C0A0`) with a chain of `cp n` tests. A second dispatcher, `00:380C`, masks A to 0-31 and jumps through the 32-word table `JumpTable_00_3822`.
* **ROM self-test (C).** `00:06F5` selects banks `$01` to `$3F` one after the other and compares the bytes at `$4000` and `$7FFF` with the bank number (a second pass at `00:0737`). That is why every bank starts and ends with its own number: the 126 bytes are typed as data with this reason.
* **Banks `$01`-`$03`: tiles and screens (C, the copy calls).** The copy routine `00:02B9` (HL source, DE destination, BC count, the bank mapped at the call) loads a 6 KB tile set from `$4001` of banks `$01`, `$02` and `$03` (bank `$03` has a second one at `$5A41`) and full-screen maps of 576 bytes (18 rows of 32) after it: 12 tile-set copies and 12 map copies with a constant source; the 11 other copies to VRAM take their source from a register (all 50 copy calls are listed in `assets/copy_sites_proto.csv`). The other copy routine, `00:2EF5` (B pages of 256 bytes, unrolled), copies SRAM photo buffers (`$A100`...) to WRAM.
* **What the bytes are.** Of the 1,048,576 bytes: 12,893 bytes of proven code; 181,351 bytes of leftover text in 53 blocks (typed `.text` by the bytes alone: printable ASCII and Shift-JIS lines ending in CR LF, outside the code and the copy sources: the assembly source and listings with Japanese comments); 190,122 bytes of padding (runs of 16 or more `$00`, cut where a label falls inside a run); 401,081 bytes of data typed by a reason (copy sources, the two symbol tables, the self-test bytes, the jump table, the DMA stub, the TCRF unused assets and the leftover copies and variants of identified blocks, below); 263,129 bytes of data on the default typing (no reason yet: the rest of the leftover banks, tables of bank `$00`, the tile sets nothing copies). Runs of printable bytes without a line end stay data on purpose: bank `$00` has byte tables in the printable range (`00:17A1`, `00:1904`).
* **Block names.** `tools/proto_types.py` gives one label per typed block, by kind and address (`Gfx_BB_AAAA`, `Map_BB_AAAA`, `Data_BB_AAAA`, `JumpTable_00_3822`): the first layer of the L3 names below.

## L2: what runs (2026-11-09)

Runs (SETUP.md, prototype L2): the project's core (`tools/proto_coverage.py`, novelty search over key presses, 25 minutes each) on the image as dumped, from blank SRAM and from the owner's prototype save (not in git); then BGB, the judge, on the header-patched copy (`tools/proto_bgb_replay.py`), which replays for every `GAME_SEQ` value the key history that first reached it in the core. The histories are in `trace/runs/*/modes.csv`, the union of the executed bytes in `trace/cov_proto_runs.npz`.

* **Coverage (C, core).** 7,711 of the 7,915 traced instructions ran, 12,495 of the 12,893 bytes of proven code; 0 executed bytes lie outside the trace, and nothing ran outside bank `$00`: the trace's finding holds. The 29 blocks of traced code that never ran (398 bytes) are listed in `trace/observed_proto.md`.
* **Coverage map (C, core runs).** `proto_rom_reachability_map.png`, drawn by `tools/reach_map.py --tag proto` in the legend of the Japanese map (`tools/reach_draw.py`): blue = executed or read in a run, red = traced code no run executed and no verdict explains (6 bytes since 2026-11-13: the BGB runs of the tester credited, the rest given hand verdicts; purple = never run and unreachable, or run only on a faulty cartridge, 213 bytes), orange = data no run read but explained by a type row, grey-blue = data nothing explains yet (mostly the leftover banks), padding and fill. The checker redraws it. Both maps draw every byte as a tile, so the leftover pictures of the older builds (banks `$05`, `$06` ...) show in them.

![What the runs of the prototype reached](proto_rom_reachability_map.png)

* **What is behind the blocks that never ran** (read in the code; not run is not dead). The timer interrupt (`00:0050`, handler `00:1266`): the constants written to the interrupt-enable register are `$09`, `$01` and `$02`, never the timer bit, and two writes copy a variable (I: probably never enabled). The error branches of the ROM self-test (`00:0713`, `00:076A`): taken only when a bank does not hold its number (`cp d; jr nz`), never on a sound ROM (C, by the code). Link-cable code (`00:036A-0386`, `00:130B-1364`: serial registers, a link-role byte at `$C0D7`): it needs a second Game Boy, which these runs do not have. The others are not investigated yet.
* **Screens (C, BGB; 26 of 26 replays end on the `GAME_SEQ` the core reached, from both start saves).** `GAME_SEQ` (`$C0A0`) selects the screen; the main loop's dispatcher `00:01FE` has 14 cases, `$00` to `$0D`, and the runs reached `$01` to `$0D`. In BGB: `$01` title, `$02` MENU (SRAM TEST, BANK TEST, PROTECT TEST, MOVIE TEST, GALLERY, COM), `$03` BANK (`8M OK`, `4M NG` in BGB; bank `$20` mapped at the end: the self-test is running), `$04` SRAM (VERIFY, WRITE, AGING, DUMP), `$05` DATA SELECT (fill patterns), `$06` a live sensor picture with counters (bank `$04` mapped), `$07` AGING (with an ERROR box), `$08` DUMP (hex dump of SRAM bank 00), `$09` the sensor settings (dither, mode, edge, VREF, zero point, gain, offset, exposure, palette), `$0A` PROTECT, `$0B` COM (the link test: a frame with the exchanged number), `$0C` the picture save after A on MOVIE TEST (test pattern, セーブする? "save?" Yes / No; bank `$04` mapped), `$0D` GALLERY (a frame with the photo number). The menu path to each value, measured in BGB, is in `trace/menu_paths_proto.csv` (`tools/proto_bgb_scenarios.py`); TCRF describes the same screens (*Proto:Game Boy Camera*, below). The picture below comes from the blank-SRAM run only (a run from a real save can show its photos).

![The screens of GAME_SEQ $01-$0D, BGB](proto_game_seq_screens.png)

The screen tree (which keys lead where, B back, the AGING and COM conditions) is in the main README: [`proto_screen_tree.png`](proto_screen_tree.png).

**Classified (2026-11-12, `tools/red_classify.py`).** 220 bytes in 22 pieces, all in bank `$00`, each with its way in, its gate and its verdict in [`trace/red_proto.csv`](trace/red_proto.csv): the 398 never-run bytes of the core runs, less what the tester's BGB runs executed (below).

**The tester's BGB runs as coverage (C, BGB, 2026-11-13, `tools/proto_red_bgb.py`).** Every instruction of the 398 bytes is an execution watchpoint (189 points, with the VBlank vector as control) in 88 BGB runs of the tester's own scenarios: every menu path, AGING on each DATA SELECT row and from a protected cartridge, SRAM WRITE then VERIFY after PROTECT TEST > OFF, BANK and PROTECT TEST, MOVIE TEST with every key, its settings screen row by row, GALLERY, COM, four runs from a cartridge of `$FF`, and the COM link test with two linked BGB instances (`tools/proto_bgb_link.py`). BGB executed 98 of the points: the link interrupt `SIO_INT` and the COM screen (`EMI_MAIN`, `N_OBJ_HYOUJI2`, `N_TU_SIN`) in the link run, the DECREMENT pattern's check (`AGE_DEC`), the VERIFY OK path (`SRAM_VERIFY`, `VB_SRAM_MENU`), palette 3 (`CHANGE_PALETTE`), the black-picture check (`CHECK_BLACK`); with the straight line after each hit, 183 bytes, `trace/wp_exec_proto.npz` (hits per run: `trace/red_bgb_hits_proto.csv`).

**Verdicts on the rest (2026-11-13, `trace/red_verdicts_proto.csv`, one per piece).** 145 B **UNREACHABLE** (purple): `GAME_SEQ` `$0E` (never stored), the 4M OK branch (an 8-Mbit ROM), a palette above 5, `SAVE_FLAG` above 2, the timer interrupt (I), and the settings rows GAIN, OFFSET and CHG: the cursor goes `$15`, `$25`, `$35`, then jumps to `$95` (PALETTE) and back (`00:14F0`, `00:150C`), so the held Right / Left of those rows (`Seq09_ConfigMain`, 90 B) and their `Config_PutItem` cases never run; 68 B **FAULT** (purple: only on a faulty cartridge): the NG branches of BANK TEST, AGING (second byte), OFF / ON TEST and their texts; 6 B **DATA** (red: need another sensor value: the offset's sign, a brightness step of `$A6` / `$FD` or more); 1 B **RUN** (a `ret` after a loop BGB ran).

## L3: names (2026-11-09)

The names come in six layers, merged by `tools/proto_names.py` into `disasm/sym_names_proto.csv`: 1709 names (C 777 / I 932 / ? 0), the 887 leftovers among the I (and 459 more leftovers tagged C: the older builds' routines and data whose address and name a symbol table gives). They follow the Japanese ROM's naming (owner, 2026-11-09): routines keep the developers' names; an asset carries the Japanese kind prefix and its own address, with the developers' name as suffix (`Gfx_01_4001_FNTOOE1`, `Map_01_5801_TITLE1`); a run of bytes that nothing in this build reads, runs or explains is `Leftover_BB_AAAA`, tag I (owner rule 2026-11-11), with a suffix when its content is known (the leftovers section below). * **The developers' own names, from the two older builds (122 routines, labels and tables).** The ROM keeps the bank-0 code of the two builds whose symbol tables it holds: table `$2A` fits bank `$2C` (57 % of its bank-0 code labels are a `call` / `jp` target there) and table `$35` fits bank `$37` (51 %) (C, byte scan). `tools/proto_match_old.py` reads each old routine from its label to the next, masks the 16-bit operands and looks for it in this build's traced code; a label not found as code is then looked for as data (its exact bytes, outside the code): 216 of the 470 old labels are found at exactly one place (`disasm/match_old_proto.csv`). The data labels found this way name the aging patterns `PAT_DEC`, `PAT_0F`, `PAT_5A`, `PAT_00`, `PAT_FF`, the dither order patterns `BAYER_PAT` ... `CONCENT_PAT`, the exposure tables `CHG_TIME_TBL_U` / `_D`, the settings-screen texts `DITH_P0`, `EDGE0`, `VREF0`, `ZERO0`, `REV0`, the save texts `SAVE_SURU` (セーブする), `NANBANNI` (何番に, "to which slot"), `SAVESIMASITA` (セーブしました) and the OAM DMA stub `DMADATA`. The names are romanised Japanese: `GAME_TITL`, `MAIN_MENU`, `SRAM_AGING`, `KAO_ANIME` (顔, face), `WANKO` (the dog on the title screen), `AKARUSA_HYOUJI` (明るさ表示, brightness display), `BUNKATU_HYOUJI` (分割表示, split display), `N_TU_SIN` (通信, link).

## What the tester does: controls, SRAM aging, link test, dither (2026-11-09)

Each TCRF item of that page is a row of group D of `tcrf_check/TCRF_CHECKLIST.md` (D01-D14). References: TCRF, *Proto:Game Boy Camera* (tcrf.net, revision of 4 December 2025; https://tcrf.net/index.php?title=Proto:Game_Boy_Camera&oldid=1982808: the menus, the MOVIE TEST settings, GALLERY, COM, the unused pictures, two source chunks); the owner's [Inject-pictures-in-your-Game-Boy-Camera-saves](https://github.com/Raphael-Boichot/Inject-pictures-in-your-Game-Boy-Camera-saves) README (the prototype's save layout, and that its aging test needed SRAM written with particular patterns: "It must be possible to generate them onboard but I did not find how"); docs §18.14 (the sensor source left as text in this ROM). BGB runs: `tools/proto_bgb_scenarios.py` and `tools/proto_bgb_link.py`, the BGB copy, blank SRAM.

**At power-on (C).** No key is read before the title: the only joypad reader is `INKEY` (`00:02E6`, keys held in `CNT1` `$FF80`, newly pressed in `TRG1` `$FF81`; buttons A, B, Select, Start in bits 0-3, Right, Left, Up, Down in bits 4-7), and the boot code and `GAME_INIT` test no key. 41 power-on holds in the core (each key, every pair, five larger chords) end as a plain boot does, with not one more code byte run. So there is no boot menu reached by keys. A+B+Select+Start held together restarts the program at any time (`00:01C7`, `jp $0150`). The title leaves on A, B, Select or Start, not on a direction.

**Every key the program tests (C, code; 21 reads of `CNT1` / `TRG1` in all).** Beyond the menus (Up / Down / A / B):

| screen | key | effect | in TCRF |
|---|---|---|---|
| MOVIE TEST | Select | next image-copy ("trick lens") mode, `BUNKATU_MODE` `$C167`, `$00`-`$1F` | yes |
| MOVIE TEST | Left / Right held | `CONTRAST` (`$C165`, `$01`-`$83`): `SET_DITH_MATRIX` rebuilds the 48 thresholds from row C of `CONTRAST_ROWS`, `CONTRAST_HYOUJI` shows it | as "offset" |
| MOVIE TEST | Up / Down held | `AKARUSA` (`$C164`, brightness target of the exposure loop, `$00`-`$A8` by 2), shown by `AKARUSA_HYOUJI` | no |
| MOVIE TEST | A held | take a picture: the save screen (`GAME_SEQ` `$0C`, slot 00-29) | yes |
| MOVIE TEST | B | when the copy mode has bit 0 set, clears that bit (I: back to the moving picture); otherwise back to the menu | partly |
| MOVIE TEST | Start | settings (`GAME_SEQ` `$09`) | yes |
| settings | Left / Right, Up / Down held | repeat every 4 frames after a first delay (Left / Right only on three of the rows); B or Start leaves; Select is not tested | partly |
| GALLERY | Up / Down held | next / previous photo, 00-29, every frame while held | yes |
| GALLERY | B held | back to the menu (the photo number moves on by one first) | no |
| COM | A | start the exchange (this unit becomes the master) | yes |

**BANK TEST: 8M OK, 4M NG is the right answer (C, code).** `BANK_TEST` (`00:06F5`) selects banks `$01`-`$3F` and compares the bytes at `$4000` and `$7FFF` with the bank number (the reason every bank starts and ends with its number); `TEST4M` (`00:0737`) does the same but expects the number AND `$1F`, that is banks `$20`-`$3F` repeating `$00`-`$1F`, as on a 4-Mbit (32-bank) ROM. On this 8-Mbit cartridge the first test passes and the second fails, as TCRF's screenshot and BGB show.

**PROTECT is the SRAM write protection (C, code and BGB).** Only two places write the SRAM enable register (`ld [$0000],a`): `OFF_TEST` writes `$0A` (writes on) and `ON_TEST` writes `$00` (writes off), and `PICT_SAVE_GO` brackets each picture save with the same two writes. `PROT_TEST` inverts the first and last byte of each of the 16 banks and checks whether the write took. This answers TCRF's question "what is this protecting?": the whole SRAM, through the mapper's RAM enable.

**The aging test can be prepared on the cartridge itself (C, BGB, `trace/aging_bgb_proto.csv`).** AGING (`SRAM_AGING`, every frame while its screen is up) runs cycles: write the pattern chosen on DATA SELECT to all 16 banks of `$A000-$BFFF` and read it back (`AGE_DEC`: the 16-bit counter from `$55AA` down, high byte first; `Aging_FillSram`: B, B, C, C repeated with 00 / FF, 55 / AA, 00 / 00, FF / FF; the patterns are the data `PAT_DEC`, `PAT_0F`, `PAT_5A`, `PAT_00`, `PAT_FF`), add 1 to COUNT (`$C0DA`), fill the whole SRAM with `$5A`, and start again; the first wrong byte stops it and shows its bank, address, expected and read values (`AGING_ERROR`, `$C0DC-$C0E1`). Neither AGING nor WRITE enables the SRAM: on a protected cartridge every write is lost and AGING stops at once (in BGB: ERROR `00:A000 55->00`, COUNT 0000, the SRAM untouched). After PROTECT TEST > OFF the same AGING runs without error (in BGB: COUNT 0007 after about 10 s, banks 0-6 holding 55 55 AA AA, the rest the `$5A` of the previous cycle). So no external flasher is needed: **PROTECT TEST > OFF, then SRAM TEST > AGING**. The test functions also write `$01` to `$6000` before using SRAM, which the Pocket Camera mapper does not need: on an MBC1 board it selects the RAM banking mode, and the header as dumped declares MBC1 (I: the tester was written for an MBC1-style development board).

**Choosing and switching the aging pattern (C, code and BGB, `trace/aging_patterns_bgb_proto.csv`).** The pattern is chosen on DATA SELECT, never on the AGING screen:

1. Once per power-on: MENU > PROTECT TEST > OFF, then B back to the menu (without it every pattern stops at the first byte).
2. MENU > SRAM TEST > AGING opens DATA SELECT.
3. Up / Down move the cursor over the five rows; it wraps (Down on ALL FF goes to DECREMENT, Up on DECREMENT to ALL FF).
4. A starts AGING with the row under the cursor: the cursor's height is copied to `R0` (`$FF88`: `$35`, `$45`, `$55`, `$65`, `$75` for the five rows) and AGING picks its pattern from it at every cycle. Entering AGING (`MK_SRAM_AGING`, `00:0AF4-0B00`) clears COUNT and the error flag: COUNT counts from 0 for each pattern.
5. To change pattern: **hold** B on the AGING screen until DATA SELECT comes back, choose another row, A. B on DATA SELECT goes back to the SRAM menu. DATA SELECT keeps the cursor on the last row used.

| row | `R0` | written at every cycle | in BGB after about 10 s: bank 0 begins with | COUNT |
|---|---|---|---|---|
| DECREMENT | `$35` | a 16-bit counter from `$55AA` down, high byte first, through all 16 banks (`AGE_DEC`) | `55 AA 55 A9 55 A8 55 A7` | 4 |
| 00,00,FF,FF | `$45` | `00 00 FF FF` repeated (`Aging_FillSram`, B = `$00`, C = `$FF`) | `00 00 FF FF 00 00 FF FF` | 7 |
| 55,55,AA,AA | `$55` | `55 55 AA AA` repeated | `55 55 AA AA 55 55 AA AA` | 7 |
| ALL 00 | `$65` | `$00` everywhere | `00 00 00 00 00 00 00 00` | 7 |
| ALL FF | `$75` | `$FF` everywhere | `FF FF FF FF FF FF FF FF` | 7 |

Why B must be held: the keys are read once per pass of the main loop (`INKEY` has one caller, `00:01C4`), and a whole aging cycle (writing and reading 128 KB, then the `$5A` fill) runs inside one pass, so a short press made during a cycle is never seen. In BGB a 4-frame B left DECREMENT running; B held for 240 frames, then Down and A, switched to 00,00,FF,FF; B held, then A at once, restarted 55,55,AA,AA (the cursor kept). DECREMENT is the slowest pattern (4 cycles where the others do 7), as it computes every word.

**COM, the link test (C, code and two linked BGB instances).** On entering COM (`MAKE_EMI`) a unit loads `$FE` in the serial data register and waits on the partner's clock. A (`N_KEY_INPUT`) sends `$00` on its own clock. The serial interrupt (`SIO_INT`, `00:034B`; enabled from boot, IE = `$09`, and switched off where IE is set to `$01` at `00:0F5C`, `00:12EA`, `00:1DC9`, `00:1EB9`) settles the roles from the first byte it receives: the idle `$FE` makes it the master (`$C0D7` = 2), `$00` makes it the follower (1). From then on each unit shows the byte it received (`$C0DD`, two hex digits in sprites) and sends it back plus one, the master starting one transfer per frame: both screens count 00-FF in a loop (as TCRF says). There is nothing more: no data, no checksum, no end. Both units must already be on COM: with the partner left on the menu, the unit that pressed A reads `$00` from it, becomes a follower and waits for a master that never comes (in BGB: frozen on 00, the partner still on the menu with no role).

**Dither matrices (C, code; names from the old symbol table `$2A`).** The sensor thresholds are not stored as finished matrices: `SET_DITH_MATRIX` (`00:3447`) builds the 48 values from a contrast row (`CONTRAST_ROWS`, `00:3862`, 131 rows of six bytes: three bases and three widths, chosen by `CONTRAST` 1-131) and a 4 x 4 order pattern (`00:3C9A`, 16 bytes each, chosen by the ディザ setting, `$C0E9`): 12 patterns, as the 1-11 and OFF of TCRF: 0 `NO_DITHER_PAT` (all 8: the same three thresholds everywhere), 1 `BAYER_PAT` (the retail Bayer order, transposed, docs §18.14), 2 `HARF_PAT`, 3 `SCREW_PAT`, 4 `SCREW2_PAT`, 5 `TYUUKAN_PAT`, 6 `CONCENT_PAT`, then five test shapes (7-11). The retail camera has three order variants (one level everywhere, the 16-level Bayer ramp, 2 x 2 blocks of four levels; docs §18.12); the prototype has twelve, each combined with any of its 131 contrast rows.

## Leftover linker symbol tables (2026-11-08)

Besides the source text, two binary symbol tables survive: bank `$2A` (file `$A8B7F`, 674 records) and bank `$35` (file `$D4A91`, 705 records), both sorted by name from `ABORTFLAG` to `ZERO0`. A record is a length byte, the name, a kind byte (`$10` label, `$18` EQU constant, `$00` for the two `REM` records), a byte 0..6 (not decoded) and a little-endian value (C, read from the bytes). [`disasm/leftover_symtab_proto.csv`](disasm/leftover_symtab_proto.csv) lists every record; it is written by `python3 tools/proto_symtab.py $R/pocketcamera_proto.gb`.

* **Older builds, not this one (C).** The two tables disagree on most code addresses (bank-0 labels in table `$2A`: 188 with another value in table `$35`, 28 absent from it, 8 equal), and under 2 % of their bank-0 code addresses are a `call` / `jp` target of this ROM's bank-0 code. The code labels cannot be applied by address.
* **HRAM, I/O and constants are stable (C for the agreement).** All 84 HRAM / I/O names of table `$2A` have the same value in table `$35`, and so do its 51 numeric constants and its 31 banked labels; 98 of its 283 WRAM names agree (166 differ, 19 are absent).
* **Names confirmed by this build's code (C).** The main loop `00:01C8-01DD` and the VBlank handler `00:01E3` use the addresses the tables give: `FLMCNT` (`$FFAA`, incremented by the routine called at `00:01D0`, which then dispatches on `GAME_SEQ`, `$C0A0`), `MAIN_AFURE` (`$FFA9`, set to `$FF` by the main loop at `00:01D5`, read by the VBlank handler at `00:01EA`), `VBFLG` (`$FF85`, set by the VBlank handler at `00:01F4`, awaited and cleared by the main loop at `00:01D7-01DD`) and `BANK_BUF` (`$FFFD`, the copy of the ROM bank number kept next to the writes to the bank register `$2100`: 21 occurrences of the bytes of `ldh [$FFFD], a` in bank 0 (a byte search, not a trace), e.g. `00:0552` just before `ld [$2100], a` at `00:0554`). What each variable means beyond these accesses is I.
* **Every other row is a candidate (I)** until the trace of this build confirms it. `DEBA_BROWSE` is a code label in both tables (`$06A7` in `$2A`, `$09A1` in `$35`): a routine of the older builds, not located in this one yet.
* **A third list, as held in memory (I, 2026-11-12).** Inside the leftover PC memory, runs of the same records with the kind bytes `$D0` (label) / `$D8` (EQU), the kinds above with bits 7-6 set: 34 records in bank `$11` (`LOOP_COUNT` ... `MIRROR_MODE`, three runs) and 34 in bank `$1E` (`B_GAIN` ... `B_TH220`), listed in [`disasm/leftover_symtab_mem_proto.csv`](disasm/leftover_symtab_mem_proto.csv) (`tools/proto_symtab.py --out-mem`). The bank `$1E` run agrees with table `$2A`; the bank `$11` runs are a third build (20 of their 34 values differ from both tables, `MABIKI2` `$C0D6` against `$C0D0`).

**Leftover source text (2026-10-26).** About 160 KB of the developers' build files survive as Shift-JIS text in the ROM (`Leftover_BB_AAAA_AsmSource` / `_SrcListing`, listed in `assets/text_sections_proto.csv`): assembly source with Japanese comments in banks `$1E`, `$1F` and `$24`-`$27` (the sensor driver, the exposure loop, the dither tables; several copies at different stages), symbol listings of the source files (`siowork.dmg`, `f_screen.dmg`, `gallery.dmg`, `def.dmg`, `equ.dmg`, `bk7.dmg`) in banks `$12`-`$15`, and `DEFB` data tables. The sensor routines and how they differ from the retail ROM are in [`docs/18_sensor_registers.md`](../../docs/18_sensor_registers.md) §18.14 and [`docs/19_sensor_guide.md`](../../docs/19_sensor_guide.md) §19.9: a linear offset search until a whole 8 x 8 tile in the middle of the picture is black, one register set, an exposure floor of `$21`. The running copy of that code is compiled in bank 0 (`CHECK_BLACK` at `00:37B8`).
